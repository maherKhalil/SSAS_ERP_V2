**T-107 added `salaryType` to `RecordCompensationRequest` and NOT to the route's strict-schema dictionary.**
The reader rejects any member it does not declare, so **a client sending a salary type got a 400, and a

opened.** That is `PayElement.OvertimeTier`'s exact shape — a capability wired at four layers with the fifth
never written — **which I have been finding all week and then produced.**

**Fixed here rather than deferred:** it is one dictionary entry and one attribute in a file this task was
already editing, and shipping a *new* API surface beside a broken one would have been indefensible.

## The defect and the feature really are one line

```csharp
if (inForce is null && (employeeOneOffs is null || employeeOneOffs.Count == 0))
{
  continue;
}
```

**The original rule was right about one case and silently wrong about another.** *"An employee with no
compensation on file is SKIPPED, not defaulted to zero — an absence is the truth"* holds for a salaried
employee whose record is missing. **It was never true for someone who was never meant to have one**, and the
model could not tell them apart. **Now it can:** no compensation and no one-off is still an absence; no
compensation *with* a one-off is a person to be paid.

## The null compensation needs no special path

No base, no assignments, no proration, no absence deduction — **every element yields zero and the zero-line
rule suppresses them.** What remains is exactly the one-off. `An_employee_with_no_compensation_is_paid_their_one_off`
asserts both halves: the one-off line is there and **there is no zero base line.**

# A REFUSAL THAT WOULD OTHERWISE HAVE REPRODUCED THE BUG ONE LEVEL IN

The run prices active elements and never `NetPayPayable`. **A one-off naming anything else would have
produced no line — an instruction somebody wrote, a person expecting money, and nothing anywhere.**

**That is precisely the defect this task exists to close**, so `PayrollErrors.OneOffPaymentElementNotPayable`
fails the run instead. The element is also checked when the instruction is *written*, so the ordinary case is
caught on the day somebody types it rather than on the day payroll is calculated.

# CONSUMPTION

**At approval, in the approval's own transaction** — `SetCalculation` refuses only `Approved` and `Posted`,
so a draft may be recalculated or abandoned, and an instruction consumed there would be consumed by
something that might never pay anybody. **Re-running before approval re-includes it and produces the same
line: idempotence for free, with no flag to reset.**

**A reference, not a bool** — `IsConsumed` is derived from it, so there is one fact and it names the run.
**`MarkConsumedBy` refuses a second run** rather than no-opping, which is what makes double payment
structurally impossible instead of guarded by whoever remembers to check.

## Reversal is recorded as UNRESOLVED, with the reason rather than the absence

Written into the aggregate: **not *"we chose not to handle reversal"* but *"a reversal does not mark the run,
and a reversed run cannot be corrected at all — so there is nothing for a one-off to survive into."***
Both halves are cited to the code that shows them. **T-111 is when this becomes answerable.**
