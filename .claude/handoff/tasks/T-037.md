# T-037 — A capability guard for cardholder data, repository-wide

- **Branch:** `agent/T-037-cardholder-capability-guard` — branch from `main`
- **Module:** Platform / BuildingBlocks / Tests
- **Issued:** 2026-08-26
- **Depends on:** T-046 merge. **Gated.**

## Goal

`ADR-029` decision 4 rules that **no SSAS type may declare a property capable of holding cardholder
data** — capability, not content: *a nullable `CardNumber` that is never populated still violates it,
because the boundary is the absence of a place to put the data rather than the discipline of not
putting it there.*

**It has had no executable guard since T-010**, and I recorded then that it was enforced by reading —
the state T-015 spent a whole task removing elsewhere. T-046 has just de-conditionalised
`REQ-SUB-0026`, so *the product performs payment capture* is now a settled requirement rather than a
conditional one. **The rule matters most at the moment its subject stops being hypothetical.**

Your own framing is the spec: not *"no type may be named `Billing`"* but **"no type may declare a
property capable of holding cardholder data"**, repository-wide rather than over one slice — because a
name-based guard would not catch a `CardNumber` property on a type called `PaymentRecord`.

## Acceptance criteria

- [ ] **An architecture guard asserts the rule across every production assembly**, not only the
      commercial plane. T-035 asserted it over seven types; this is the rest.
- [ ] **It matches capability, not naming.** A property whose name or type could hold a PAN, CVV,
      cardholder name or expiry is a finding wherever it lives. **Say in the test what shapes it
      recognises and, explicitly, what it cannot** — `DEC-L-031`: a guard oversold is a guard trusted
      past its reach.
- [ ] **`DEC-L-031` proved in both directions.** Red: introduce such a property, watch it fire, remove
      it, show the removal was exact. Green: it passes on `main` as it stands. **And `DEC-L-043`: if it
      passes first time, name the specific way that pass could be hollow and rule it out** — a
      capability guard that matches nothing anywhere is indistinguishable from one that works.
- [ ] **The realistic failure is named in the test.** `ADR-029`'s risks section says nobody will propose
      a `Pan` column; the actual erosion is **a free-text `Notes` or `Metadata` field on a payment type
      that a support process pastes a card number into.** A guard that only catches the obvious case
      should say so rather than imply coverage it lacks.
- [ ] Gate green under `DEC-L-008`, **Integration runs**, merged on green. Baseline: Architecture 476,
      Platform 1032, API 724, HR 326, Finance 46, Payroll 56, Attendance 59, **Integration 803 both**.

## Design constraints

- **Capability, not content, and not naming.** The three are different tests and only the first is the rule.
- **A finding in production code is a `NEEDS-DECISION`.** If the guard fires on something that exists
  today, stop and report — do not delete a property to make a gate green.
- **`AC-SUB-0048`/`TS-SUB-0047` in FP-014 specify this criterion.** Read them first; if what they
  specify differs from what this task asks, **that is a finding and the package wins.**
