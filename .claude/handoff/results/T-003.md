## I tested the three reasons rather than transcribing them — and the third needed correcting

You asked me to push back if the reasoning did not survive contact with the documents. Two survived
as given. **One is true for a subtler reason than the ruling stated, and stating it your way would
have left a future reader able to disprove it.**

### Reasons 1 and 2 — hold as given

**Residency.** `ADR-017:167` reads *"Tenant identity/access membership remains Platform database data
even though it is tenant-scoped. This is a **deliberate refinement** of the naive rule 'everything
`ITenantOwnedEntity` moves to the tenant database'."* Exactly the case, already decided.

**Optional on both sides.** `Employee` carries no `IdentityId`, `TenantUserId` or `UserId` — confirmed
by reading the aggregate, not by inference. And a tenant user need not be an employee.

### Reason 3 — the correction

You wrote: *"`Employee` is in the cutover inventory while `TenantUser` is not."* True in effect. **But
`TenantUser` IS `ITenantOwnedEntity`** — `public sealed class TenantUser : AggregateRoot<long>,
IAuditableEntity, ITenantOwnedEntity`.

So the marker is not what excludes it. `TenantCutoverCopyPlan.Build(IModel model)` filters by
`ITenantOwnedEntity` **within the model it is handed**, and it is handed the tenant model.
`TenantUser` is registered in `PlatformDbContext` and appears **zero times** in `TenantDbContext`. It
is outside cutover because it is outside the *tenant model* — **cutover membership follows model
residency, not the marker interface.**

**Why this matters enough to correct:** a future reader challenging the ADR would check *"is
`TenantUser` `ITenantOwnedEntity`?"*, get **yes**, and conclude the ADR's third reason was false. The
reason is sound; the shorthand for it was not. The ADR states the mechanism.

It is also a second instance of the `ADR-017` refinement the first reason cites — the naive rule would
say `TenantUser` moves, and it does not.

## One decision I added that `DEC-L-023` did not contain

**Decision 5 — absence is an ordinary answer, never an error.** Resolution is a lookup, and *"this
caller is not an employee"* is a normal result every caller must handle.

It falls out of decision 2's optionality rather than adding anything to the ruling, and it is stated
separately because **that is where an implementation goes wrong silently**: a developer tests with an
employee-linked user, every path works, and the support administrator finds the crash in production.
A support admin opening a self-service page is not a fault condition.

If you read that as exceeding the ruling, it is one decision and it deletes cleanly — but it is the
one I would most expect to be needed.

### The alternative I rejected most firmly, and why it is worth a line

**Deriving the link from matching attributes** — email, employee number, name. The ADR rejects it
outright rather than listing trade-offs, because it is the alternative most likely to be reached for
under delivery pressure: it needs no new storage and appears to work immediately.

It is not a mapping but a guess; it fails silently when the attributes diverge; and it makes a
person's access to their own payroll data depend on a string comparison. That is the one alternative
where a balanced treatment would have been the wrong service to a future reader.

### Follow-ups noticed but not done

- **The five open questions are the implementing package's**, and one of them reaches further than the
  others: whether *view my own payslip* is a distinct permission from *view an employee's payslip*.
  **Every consuming module needs that answered** — Payroll, Attendance, and whatever Self Service
  becomes — so it is a candidate for an owner decision early in that package rather than late.
- **`ADR-015`'s plane separation is load-bearing here and nothing asserts it for this mapping.** The
  risk section names it: the mapping answers *which employee is this user*, and it would be easy to
  let it start answering *what may this user see*. When the package exists, that is a candidate for an
  architecture guard of the kind T-015 built — a property about surface, not a convention about
  intent.
