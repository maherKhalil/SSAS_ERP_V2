# ⚠ HALF ONE IS A LIVE SILENT FAILURE, AND IT IS ON THE CUTOVER'S DATA-LOSS PATH

**`TenantCutoverWriteFence.cs:99`:**

```csharp
if (gate.IsFirstTargetWrite)
{
  await operations.RecordPostCutoverWriteAsync(gate.CutoverOperationId, PostCutoverActor, cancellationToken);
}
```

**`RecordPostCutoverWriteAsync` returns `Task<Result>`. The result is discarded.**

**And it can fail.** `TenantCutoverOperationStore` ends:

```csharp
return observed is not null
  ? Result.Success()
  : Result.Failure(TenantStorageErrors.CutoverConcurrencyConflict);
```

**A write-once update that did not take — which is precisely what happens when two writers race during a
cutover, the one condition this mechanism exists for.**

## Why that matters more than a dropped return value usually does

**This observation is the record of whether ANY application write has reached the cutover target.** That
record is what decides whether a flipback to the old database is safe.

**When the record silently fails: the tenant write lands, and the platform still believes no post-cutover
write has occurred.** A flipback then looks safe and **would discard a committed write.**

**The branch's own added comment says exactly this** — *"the caller must refuse the write rather than let a
genuine target write land while the platform still believes none has"* — **so the author knew. The fix was
written on 17 August and has sat unmerged in a local-only branch since.**

**This is not preventive and I would not describe it as hardening.** It is `chain-test`'s shape: a real
defect sitting in an unpushed branch nobody swept.
