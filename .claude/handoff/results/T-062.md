## The three pieces

**Piece 1 — rule 4 reads `test-scenarios.md`.** It was wrong about a *fact*: `AC → TS` is not recorded
only in the matrix. The pairing must be **on one row**; a file-wide test would make rule 4
unfalsifiable, since every criterion co-occurs with some scenario in a file listing both.

**Piece 2 — ranges expand**, in both spellings the corpus uses. A reversed span expands to nothing
rather than to a guess; a span wider than 200 is refused so a typo cannot mark a package covered.

**Piece 3 — the chain parser is anchored by `REQ-`, `BR-`, `BRULE-` or `DEC-`, and finds criteria and
tests by CONTENT rather than by column offset.** FP-003's chain table has seven columns; reading cell 2
and cell 3 is why a table could match the anchor and still yield nothing.

## Two criteria that were enforced and untested

`AC-IAM-0012` (cross-tenant assignment rejected) and `AC-IAM-0022` (a stale update is rejected without
overwriting newer data). Both invariants were **already live in the code** — which is what makes them
worth testing: an enforced guard with no test can be removed by a refactor and nothing catches it.

**`AC-IAM-0022` is two properties with two owners**, and testing them as one is what made it look
expensive:

- *"rejected"* — a handler test: a stale `ExpectedRowVersion` yields `ConcurrencyConflict` **and the
  unit of work is never asked to save.**
- *"without overwriting"* — a **model** test: `TenantUser.RowVersion` is a concurrency token in the
  built `IModel`. A round-trip would test EF Core's rowversion implementation, which is Microsoft's.
  **What can regress is someone deleting `.IsConcurrencyToken()`** — caught here in milliseconds
  instead of in a 33-minute Integration leg. **No database, no Integration, no condition 3.**

**Both have negative controls** — same-tenant assignment succeeds, a matching row version reaches the
save. Without them the tests pass against a guard that rejects unconditionally.
