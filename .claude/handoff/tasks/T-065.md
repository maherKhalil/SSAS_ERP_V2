**This is T-060's scoped-out question and the last unclassified thing in the corpus.** Two remedies,
and the distinction is **per identifier, not per package**:

- **Deleted** — a scenario was removed deliberately. **Declare the gap**; the mechanism exists and
  FP-013 and FP-014 already use it.
- **Lost** — a scenario existed and its number was orphaned by an edit. **That is a missing test
  scenario**, and reporting it is the finding; authoring it is not this task.

**Establish which from the package's own history and text — `git log` on the file will show a
deletion.** Do not infer from the shape of the range: a contiguous run tells you one cause touched
all of them and nothing about what the cause was (`AC-GL-0017`..`0021`, four hours ago).

**If a package's gaps are mixed, say so per identifier.** The tidy answer — *"FP-001's are all
deleted"* — is the one that makes the task finish faster, which is the direction that never feels
like it needs checking.

## Part B — wire `trace-check.py` into the gate, against a baseline

**`trace-check.py` is in neither `ci.yml` nor `gate.sh`.** Nothing runs it, which is why nine red
packages sat unremarked for weeks. **That is the last instance of the shape this repository removed
today**, and it is now safe to close because the number means something.

**Ruled: a baseline, not a hard zero.** The same mechanism you built for `DEC-L-008` condition 4, for
the same reason:

- **The gate goes RED when the failure count RISES above the committed baseline**, per package.
- **It does not go red on the standing count.** Eleven declared-pending items are a list of work; a
  gate permanently red on them is a gate switched off by the second week — **which is precisely how
  the nine red packages went unnoticed.**
- **The instrument writes the baseline on a green run**, committed with the work, visible in the
  diff. It cannot drift, and a package's count moving is a reviewable line.
- **A package going from failures to zero LOWERS its baseline.** Improvement must ratchet, or the
  first person to fix something hands the next person room to break it.

**`GATE_SCOPE=TASK` must still be 72 seconds.** Measure `trace-check.py`'s runtime and report it. **If
it is material, it belongs in `PHASE` only and you should say so** rather than accept a slower
per-task gate to close a documentation loop.
