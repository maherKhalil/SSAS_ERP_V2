## What was wrong

`PersistenceDbContext.OnModelCreating` set `DeleteBehavior.Restrict` on **every** foreign key, ownership
keys included. The migrations snapshot format **serialises no delete behaviour for an owned
relationship** — ownership implies `Cascade` on rehydration — so the model disagreed with its own
snapshot **permanently and unfixably**, and the differ was right to report it.

**Every migration scaffolded in this repository carried six spurious foreign-key operations.** It cost
two wrong diagnoses (T-041's tool-skew claim, T-043's `global.json` cause) before anyone read the loop,
**which carried no comment at all** — in a file whose next block spends a paragraph on why auditing hooks
the innermost `SaveChanges` overloads.

## Where I disagreed with the spec, and where it did not change the answer

The spec argued `Restrict` on an ownership key is **semantically meaningless**. **It is not.**

Through EF it is inert: owned rows are deleted with their owner by definition, and EF ordered those
deletes itself. **Via raw SQL it is not** — `DELETE FROM SubscriptionPlans` against a plan nobody is on
**failed** under `Restrict` and **succeeds** under `Cascade`, taking the plan's module grants, limits and
prices. T-035 already ships a test establishing that raw SQL is outside the write boundary, so the route
is live rather than theoretical.

**Why it does not change the answer, in the order that matters:**

1. **It was never a protection anyone chose** — a side effect of a blanket loop with no comment is not a
   design decision being reversed.
2. A plan **any tenant is on** is still protected by `TenantSubscriptions`' reference key, which keeps
   `Restrict`. The exposure is a raw delete of a plan nobody is on.
3. `SubscriptionPlan`'s lifecycle **has no removal** — retired, never deleted, because historical
   records point at it.

**The precision mattered because the file now has to say what was given up.** "Meaningless" would have
licensed a claim that nothing was lost.

## The migration is hand-written, and that is the finding

**EF generated it empty.** Migrations diff **the snapshot against the model, never the database against
the model** — and the snapshot never recorded `Restrict`, because it cannot. So after the change
model = `Cascade` and snapshot = `Cascade`, and the scaffold is empty. **Criterion 1's demonstration
succeeds.**

**But the database still had `Restrict`**, and no future scaffold would ever notice. **Left there, the
change would have traded a loud divergence for a silent one** — six operations in every migration is a
self-announcing nuisance; a schema that quietly disagrees with the model, with nothing that will ever
report it, is worse.

So `Up` was written by hand, and the migration says EF generated it empty and this is the only
reconciliation that will ever be offered. `Down` restores `Restrict` exactly.

## `DEC-L-048` — the test that was asserting a mechanism it never named

**The single failure was `A_persisted_subscription_record_cannot_be_deleted`, and it was T-047's.** It
asserted that `Remove()` **threw at tracking time**, because removing the principal severed a required
owned relationship — **and that severing was the `Restrict` side effect this task removed.**

**T-035 knew it was asserting the weaker of two mechanisms and said so**, which is the sentence the
ruling turned on:

> *"The record is protected either way — and it is protected by two independent mechanisms, only one of
> which is the append-only guard. **Remove the guard and this test still passes**, which is exactly why
> the grant test below exists."*

**Half the mechanism was evidence rather than reasoning**: the assertion that failed was
`Assert.Throws<InvalidOperationException>(() => Remove(record))`, so `Remove` demonstrably no longer
throws. **The other half — that the delete now reaches `SaveChangesAsync` and the guard refuses it — was
inference, and was flagged as inference** until the rewritten test executed it.

**I did not change the test on my own judgement.** Editing an assertion in response to a red gate is the
shape the charter forbids, and *being able to argue it is legitimate* is exactly why it was not mine to
decide. The architect ruled `DEC-L-048`; both readings were put up first, including the one against the
exemption.

### The rewrite asserts three things where it asserted one

1. **Tracking accepts the `Remove`** — stated so that a future refusal at that point names which
   mechanism is doing the work.
2. **`SaveChangesAsync` refuses, naming the append-only rule.**
3. **The row survives** — because *a refusal thrown after writing would satisfy the first two and still
   have deleted the record*. Asserting the exception without asserting the state is how a guard gets
   credited for a rollback it did not perform.

**It is stronger than it has ever been**: it passed before whether or not `PreventAppendOnlyMutation`
existed, and fails now if the guard is removed. It also closes a hole nothing else covered — no test
demonstrated the guard refusing a **`TenantSubscription`** delete, only a `TenantEntitlementGrant` one,
which owns nothing and so never had the severing to hide behind.

### And the reason it could have gone green for the wrong reason

`Remove` now marks the owned `SubscriptionTerm` entry `Deleted` too. **`SubscriptionTerm` is a value
object and not `IAppendOnlyEntity`**, so it is not among the entries the guard scans and the refusal can
only be the principal. **Had it been append-only, the test would have passed on a refusal about the wrong
row.** Established from source before the rewrite was written — `DEC-L-046`, reaching forward: the fix was
validated against a case whose answer had to be established first.
