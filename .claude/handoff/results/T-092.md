# THE DECISIONS, AND THE ONES THAT INVERT AN EARLIER RULING

## 1. `Unknown` and `Ended` answer DIFFERENTLY here — the seam collapses them

`UserEmployeeResolver` folds both into one refusal because its caller is an END USER and telling them apart
would disclose that a record exists.

**This caller is a tenant administrator acting on an employee they named and can already read.** Merging
them would leave an administrator unable to tell a typo from a former employee, and distinguishing them
discloses nothing they do not already have.

**Stated at the call site and asserted as two different codes**, so a future reader who "fixes" it to match
the seam fails a test and meets the reason. `An_unknown_employee_and_a_terminated_one_reach_the_wire_as_
different_statuses` also pins it at the mapper, because a mapper folding both into one status would undo
the distinction at the last step.

## 2. The DI shape fired a third time, and the resolution is the OPPOSITE of T-091's

```
Unable to resolve 'IEmploymentStandingDirectory' while activating
  'LinkEmployeeToTenantUserCommandHandler'
  ... PlatformSupportAuthenticationEndToEndHost, PlatformSupportAuthorityEndToEndHost
```

**T-091 made `ITenantUserDeactivator` REQUIRED**, because an absent deactivator would have meant *skip the
guard* — fail open.

**Here the dependency is OPTIONAL and absence refuses**, because absence means *no HR module, therefore no
employees, therefore nothing to link* — the same thing it meant for T-090's resolver.

**The question is never what the previous task chose. It is what ABSENCE MEANS.** Named cost: a host
misconfigured without HR reports every link attempt as "employee not found" rather than as a missing
module — diagnosable, since nothing can be linked at all, and the alternative was writing rows whose
subject nobody verified.

## 3. Unlink had to ship, and an upsert was the wrong shape

At most one live link each way, two unique indexes, removal physical, no soft delete. **A mistaken link
occupies both slots**, so creating the correct one collides and is refused rather than repaired. Without a
removal route the FIRST mistake would be permanent.

**The upsert alternative hides a destructive act inside a creative one** — reassigning which employee a
login maps to would read as "create a link" in an audit trail. Given what the link decides, that act has to
be nameable.

**POST to a named sub-resource**, and `The_host_mounts_no_delete_route_at_all` now asserts across the whole
host that this product still has no `MapDelete`. T-092 was the obvious place to introduce the first one.

## 4. Link is idempotent; unlink is not — deliberately

The identical pair answers success so a retry after a lost response does not refuse completed work.
**Removal refuses when there is nothing to remove**, because *"no link"* and *"I just removed the link"* are
the same wire answer only if the caller never needed to know which happened — and a typo in the tenant user
id would otherwise look like a completed correction.

## 5. A deactivated user CAN be linked

T-091 deactivates the account on termination, so refusing here would make a link unrepairable exactly when
someone noticed it was missing. **The link is a mapping, not a grant.** `Pending` is refused — a membership
that has not been accepted has no identity to map.

## Two guards fired and both were right

**`PermissionCatalogTests` went red on the new pair**, 26 -> 28. A new permission cannot enter the catalog
without someone deciding which plane it belongs to; both are TENANT scope, because linking a tenant's user
to that tenant's employee is a tenant administering itself.

**And I had to move `UserEmployeeLink` out of `UnroutedFamilies`** — T-093 recorded it as unrouted one task
earlier, and T-092 routed it.

**That move was made by a person, not by the guard, and the register now says so.** The staleness check
catches a family that stops DECLARING errors; it cannot catch one that gains a ROUTE, because that needs
the route-to-mapper derivation the file explains is not tractable. **The one time it happened, the someone
was the task that caused it** — which is luck, not a mechanism. T-094's transitive walk is what would make
it mechanical.
