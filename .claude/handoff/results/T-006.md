## What changed

Three files, 847 lines. Nothing else.

### The two mechanical constraints, both read out of the code rather than assumed

**1. Append-only means no closing column.** The obvious model — `EffectiveFromUtc` +
`EffectiveToUtc`, where a plan change closes the old row — **is wrong here, and wrong for a reason
this repository already wrote down.** `EmployeePositionAssignment` says it: *"There is no
`EffectiveToUtc`, because closing an interval would mean UPDATING the previous row, which is
precisely the history mutation this model exists to prevent; the interval is derived by ordering."*

So a subscription record carries `EffectiveFromUtc` and nothing that closes it. **"Exactly one in
force" is a derived invariant, not a column.** I added the invariant that falls out of it and is easy
to lose: **the append is monotonic** — strictly greater than the current maximum — because without it
an append could insert *behind* the present and rewrite what was in force when a metered overage
happened.

**2. `PreventAppendOnlyMutation` does not exist on the Platform database.** The guard is
`TenantDbContext.cs:484`, called from `TenantDbContext.SaveChangesAsync` and nowhere else. Every
commercial record here lives in the **Platform** database (`ADR-017:162`, `:475`), and
`PlatformDbContext.SaveChangesAsync` — `PlatformDbContext.cs:107` — calls no such guard.

**`OD-SUB-0008` therefore rests on a mechanism that is absent from the side of the product where
this data lives.** Recorded as a build obligation in both `domain-model.md` and `data-model.md`:
carrying `IAppendOnlyEntity` without the guard would give the model the appearance of immutability
and none of it.

### The two flagged interactions, and how each is modelled

**The cap in force is a property of the subscription record, not the tenant** — you flagged it twice
and it drives two things. `EntitlementAt` takes the instant as a **parameter**: with `T = now` it
answers "may this request proceed"; with `T = the instant a seat was observed` it answers "was that
seat within cap". And `TenantSeatUsageSamples` **stamps** the `TenantSubscriptionId` in force at
observation rather than leaving billing to re-derive it — chosen and justified in the document,
because an invoice line must be reproducible years later and must not change because the history
gained a row.

**Additive-never-lowers is structural, not procedural.** `cap(k) = max(plan, grants)`, so a grant
naming a lower value **cannot lower anything even if one existed**. A write-time refusal sits on top
so the mistake is still loud at the moment someone makes it. The data model states plainly that no
`CHECK` enforces this and why one cannot — the comparison is two joins away and varies with time —
so nobody concludes the constraint was forgotten.

### `T-010` is respected in both directions

The model stops where capture mechanics begin, and says so in three places. But it also makes the one
statement that **is** a modelling statement rather than an architectural one: **no entity in this
package carries a column that could hold a PAN, a CVV, a cardholder name or an expiry date.**
`SubscriptionPaymentAttempt` holds an opaque `ProviderReference` and the data model says the column
list is complete *and that this is the point*. If a design later needs such a column, that is `T-010`
reopening, not a schema addition.

### Choices made where the ruling set is silent — all named in-document

- `SubscriptionPlan` carries `Draft`/`Active`/`Retired`, because deleting a plan a historical record
  points at would break `REQ-SUB-0028`'s reconstruction.
- `TermKind` alongside a nullable `TermEndUtc`. `OD-SUB-0009` asked for an **explicit** perpetual
  marker, and a bare null cannot distinguish *perpetual* from *not yet set*.
- Concurrency on the subscription append: a lock on the tenant row **plus** a unique
  `(TenantId, EffectiveFromUtc)`. `EmployeePositionAssignment` rides on `Employee.RowVersion` because
  a position change also writes `Employee`; **nothing on `Tenant` changes here, so there is no
  equivalent bump to ride on** — that gap is the reason both mechanisms are specified.
- `InvoiceNumber` unique **vendor-wide**, not per tenant.
- Revocation of a grant is a superseding grant row carrying `ExpiresUtc = now`, not a fourth
  `GrantKind`.
- `ModuleDefinitions` uses an `nvarchar` natural primary key, with the departure from the
  `uniqueidentifier` norm argued and an explicit "if the build disagrees, a surrogate with a unique
  natural key is the right disagreement".

### The sharpest thing in the lifecycle document

**Expiry is derived — nothing is written when a term lapses — and that is exactly what a naive cache
erases.** `OD-SUB-0004` ruled invalidation-on-change, never TTL. But expiry has **no** change to
invalidate on. So a cache storing only `enabled: true` is wrong from the instant `TermEndUtc` passes
and stays wrong until something unrelated evicts it. The document states that the cached value must
carry the term and be evaluated against the clock, or be keyed so it cannot outlive `TermEndUtc`.
The plan-edit invalidation fan-out is called out for the same reason: editing a shared plan changes
the entitlement of **every tenant on it**, and an invalidation keyed only on `TenantId` misses all of
them.

### Two build obligations that must not be discovered late

1. **`PlatformDbContext` needs `PreventAppendOnlyMutation`.** Detailed above. Three tables in this
   package are append-only and the ruling that made them so is **unenforced on the Platform side
   until that lands**. This is the finding I would most want checked, because it is the one where the
   document could have quietly claimed a property the code does not provide.
2. **No backfill, and no default plan — and the two must not ship in the same release.** A tenant
   with no `TenantSubscriptions` row has no entitlement and reaches no gated module, which is the
   correct reading of `CON-0001`. It is also how you lock out the entire existing estate if the
   migration and the enablement gate land together with nobody having assigned plans first. **Which
   plan each existing tenant gets is a commercial decision, not a migration default**, so I raised it
   as a sequencing obligation rather than inventing one. It interacts with your `OD-SUB-0003` ruling
   that the gate ships before the next module.
