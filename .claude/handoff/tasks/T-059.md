# T-059 — Condition 4: make the gate compare the counts it already prints

**The gate prints per-suite counts and compares them to nothing.** There is no baseline anywhere in
`scripts/gate.sh`. `CODER.md`'s *"the baseline is recorded on the board"* is a true statement about
the board that says nothing about the instrument.

Found 2026-08-27 by the coder while drafting wording for the other three conditions — **it checked
the one it was not asked about.**

## Why this one is the most dangerous of the four

Conditions 0, 1 and 2 are now enforced. **Condition 4 is the one most likely to be believed
*because* the others are.** A reader who has watched the gate go red on a warning and red on a failed
build reasonably assumes the count line is checked too. It is printed and discarded, which is the
same shape as the build status before T-058 and the memory sampler before T-056.

## What is mechanisable, and what is not — do not blur them

**Mechanisable:** *the counts did not move while `src/` changed.* Record a baseline, compare, and
say something when code changed and the totals did not.

**Not mechanisable:** *the tests the task required exist.* The gate cannot know what a task required.
**Any wording implying it does is worse than the current silence**, because it converts an honest
convention into a false enforcement — and this repository has now recorded four instruments that
reported on a domain narrower than their wording implied.

**So the deliverable is a partial enforcement that says it is partial**, in the log and in `CODER.md`.
If it cannot be made to say that clearly, bring that back rather than shipping it.

## Questions to settle before building — bring answers, not a menu

1. **Where does the baseline live, and what updates it?** A file in the repo is visible in diffs and
   goes stale silently. Deriving it from the previous run needs somewhere to persist. **A baseline
   nobody updates becomes a warning everybody ignores** — that is the failure mode to design against,
   not the storage question.
2. **What counts as "`src/` changed"?** The gate does not currently look at the diff at all, and
   `DEC-L-051` refused a diff inference for Integration on the grounds that a permissive error is a
   silent hole. **Establish whether this needs the diff, and if it does, whether an error is
   permissive or conservative here.** They are not the same trade as condition 3's.
3. **Red or warn?** `T-056` refused because proceeding destroys a run; `T-058` warned because the
   signal was self-admittedly stale. **This is a third case: the signal is exact, but its meaning is
   inferential** — counts can legitimately stay flat. Argue it from that, not from the other two.

## Done when

- A change that touches `src/` without moving any test count produces the ruled outcome,
  **demonstrated by planting one**, as the build failure and the warning were.
- A legitimate flat-count change — a docs task, a rename — does **not** trigger it, demonstrated.
- The log states what was compared and against what, including when it could not compare.
- `CODER.md`'s condition 4 says exactly what is now enforced and what remains yours. **Propose the
  wording; the architect commits it.**
- `GATE_SCOPE=TASK`. No persistence touched, so no Integration and no `PHASE`.

**Check back before implementing.** All three questions above are rulings, not details.
