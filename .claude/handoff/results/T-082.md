## The four behavioural tests, and why each has a control

**Run against real SQL Server 2022 — all four green**, 60s:

```
A_link_resolves_an_employee_from_a_tenant_user                                      PASS
A_second_link_for_the_same_tenant_user_is_refused_and_a_different_user_is_accepted  PASS
A_second_link_for_the_same_employee_is_refused_and_a_different_employee_is_accepted PASS
A_link_naming_another_tenants_user_cannot_be_stored                                 PASS
```

**These are claims about SQL Server, so asserting them against an EF model would assert the intent
rather than the thing.** Each refusal is paired with the neighbouring case that must succeed:

- *same user refused* — **control:** a different user in the same tenant **is accepted**. Without it the
  test would pass against a unique index on `TenantId` alone, which would allow **one link per tenant**.
- *same employee refused* — **control:** that same second user with a different employee **is accepted**,
  so the refusal was the employee index and not something about that user.
- *another tenant's user refused* — **control:** the **very same user id**, under its own tenant, **is
  accepted**. That is what shows the refusal was the tenant mismatch rather than an invalid id.

**The composite principal key is doing the isolation.** A row naming a real user id under the wrong
tenant matches no principal and the insert fails — a database guarantee, not a handler's memory.

**Scope limit, stated:** these are Integration tests. `GATE_SCOPE=TASK` does not run them, so the gate's
green does **not** cover them; they were verified by a filtered run reported above. The TASK gate covers
the entity, configuration, migration compilation and the residency guard.
