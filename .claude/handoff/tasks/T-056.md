# T-056 — Two concurrent gates silently destroy each other's databases

**Queued behind T-055. Do not start while T-055 is in flight** — same file, and note 7 of its own
header records what editing a running gate costs.

## The defect

`reap_to_zero` drops every `SSAS[_]%` catalog on the box before each leg, under **every** scope. The
only guard against a second gate doing that mid-run is the sibling-`testhost` precondition, and it
matches on `basename "$ROOT"`.

So two working trees with **different directory names** each conclude the other's testhost belongs
to someone unrelated and proceed. A 72-second `TASK` gate in a worktree called `SSAS_gate` reaps the
catalogs a 69-minute `PHASE` run in `SSAS_ERP_V2` is using, **mid-leg, with no warning on either
side.** The `PHASE` run then fails in a way that looks like a test failure.

Found 2026-08-27 by the coder, refusing an ordering instruction from the architect that would have
done exactly this. It has not yet cost a run.

**`DEC-L-051` made this materially more likely.** A per-task gate now costs 72 seconds, and
something that cheap does not feel like an action that needs checking first.

**One live collision pair, two latent.** The two older trees acquire the hazard the moment anyone
pulls. `chain-test` is two days old — current, not abandoned — and is on a `codex/` branch, so the
colliding party may not be this loop at all and will not read this file.

Recorded at this size deliberately: the first statement of this finding said *"three other trees,
each with a `scripts/gate.sh`"*, which `git worktree list` never showed — it reports paths and
branches and says nothing about contents. **A finding overstated once is discounted the next time
it is raised.**

## The thing to get right — and the obvious fix is probably wrong

`basename "$ROOT"` → `git rev-parse --git-common-dir` is identical across all worktrees of one
repository, and closes the case above exactly.

**It does not close the general one.** Reaping matches on *catalog name*, so a second clone, a
colleague's checkout, or any unrelated tree on this box running this gate collides identically —
and repo identity would tell those two they are unrelated, which is true and irrelevant. **The
shared resource is the SQL Server instance, not the repository.**

That points at an instance-level lock rather than a smarter identity check. Not ruled — bring the
architect the shape you think is right and why. Whatever it is, it must:

- **Fail closed.** A gate that cannot determine whether another is running must abort, not proceed.
  A lock that is skipped when it cannot be read is the guard that was already here.
- **Not strand the instance.** A crashed or killed gate must not leave a lock that blocks every
  future run — that turns a silent failure into a permanent one, and the header already argues that
  *"a gate people stop running"* is the real cost of friction.
- **Survive `--blame-crash` and the abort paths.** The 2026-08-23 test host died twice; whatever is
  held must be released on those paths too.
- **Say what it is waiting for.** "Another gate is running in `<path>`, started `<when>`" — not a
  bare refusal. A guard that refuses without naming the holder gets disabled by the next person.

## Done when

- Two gates started concurrently from **differently-named** trees: the second refuses, names the
  holder, and exits non-zero with a code distinct from the existing 1–6.
- The first completes unaffected — verify by its counts, not by absence of error.
- A killed gate releases; the next run starts clean.
- `DEC-L-053`'s by-hand paragraph in `CODER.md` is replaced with what the guard now enforces, and
  says plainly which part is still the operator's to keep.
