# THE FINDING, STATED PLAINLY RATHER THAN BURIED IN A FIVE-ROW ADDITION

**Four `journal-drafts` routes were built without ever being specified, and the route table did not mention
them for the whole of FP-011.**

```
api-contracts.md:43-55   nineteen rows — journals, accounts, fiscal periods, reports
                          NO /api/gl/journal-drafts row of any verb
api-contracts.md:82-84   the family's ONLY specification, in prose:
                          "OD-GL-0007 ruled two aggregates, so a draft surface DOES exist"
```

**A surface built from a sentence.** `72cfe9b` shipped the four writes and declared `GL.Drafts.View` in the
same commit; the read it was declared for was never among the nineteen routes, and the table never caught
up with the ruling that created the family.

**That is a different failure from FP-015's.** FP-015 was a capability wired at four layers with the fifth
missing. This is a surface that had no specification to be incomplete against — which is why my Part 1
concluded "product decision" and why the architect's counter-test is the better one: **a resource that can
be created and updated but never read is not a minimal surface, it is a half-built one.**

**The four rows are documented after the fact and the omission is named in the document itself**, because a
nineteen-row table omitting a live family asserts something false by omission, and fixing it silently
inside a five-row addition would read as routine upkeep.

## The gate — Reading A, and it is the third refusal of this shape

**`GL.Drafts.View`, and nothing implies it.** The preparer holds `GL.Drafts.Manage`; the reviewer holds
`GL.Journals.Post`; **neither grants the read.**

An implied permission makes the explicit one optional and its absence unenforceable — `AC-SS-0005`, refused
for payslips in T-088 and for attendance in T-089. **Naming a draft by id on the posting route is not
authority to read it**, which is exactly the payslip question.

**Two tests carry it mechanically rather than describing it:**

```
The_manage_permission_alone_does_not_read_a_draft
The_posting_permission_alone_does_not_read_a_draft
```

Each asserts `Assert.Empty(host.Reads.ObservedScopes)` as well as the 403 — **refused at the door, so the
read service was never reached.** Without that, a handler that ran and returned an empty list would be
indistinguishable from a refusal by status alone.

**Without these two, a later "the poster obviously needs to see it" would go green** and the separation the
permission was declared for would be gone with nothing red.

## Two smaller decisions worth naming

**The response's ABSENCES are asserted, not just its contents.** `journalNumber`, `isReversed` and
`reversesJournalEntryId` are asserted *not present* — a number is assigned at posting and reversal is a
posted-journal concept, so **a model carrying nulls for both would invite a client to render an empty
number as though the draft had one.**

**The list orders by date then ID, not by number.** `SearchJournalsAsync` breaks ties on `JournalNumber`; a
draft has none, so the id is the only stable tiebreak — and a stable one is required, or two calls return
the same rows in a different order.

**The line model is reused unchanged.** `JournalDraftLine` matches `JournalLine` field for field, so a
second record would be two names for one shape and they would drift the first time one gained a column.
