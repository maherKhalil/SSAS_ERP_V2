# ⚠ TWO COMMENT CORRECTIONS, AND THEY ARE NOT THE SAME KIND OF ERROR

## 1. An overclaim about what a check catches — visible from the code alone

```
"...the operation may have moved on, or A FURTHER CUTOVER MAY HAVE MADE THIS PHYSICAL DATABASE THE WRONG ONE."
```

**`ReadWriteGateByOperationAsync` filters `operation.Id == cutoverOperationId`.** A further cutover is a
**different row with a different Id**, so a by-Id read cannot see it. The clause after the *"or"* is not
implemented by that check.

**The protection is real and lives at admission** — `FindActiveWriteGateAsync` orders by `Id` descending and
hands the fence the newest operation for the tenant.

**Anyone reading the method could have found this.** It is a reasoning error about code that is all present.

## 2. A claim that was true of a different base — invisible without knowing what changed underneath

```
"...the call fails — while the tenant's write, WHOSE RESULT WAS PREVIOUSLY DISCARDED, COMMITTED ANYWAY.
 That is the FALSE-NEGATIVE direction..."
```

**True of the branch's base. Not true of ours.** T-135 stopped the fence discarding that result **this
afternoon**, so the write does not commit and the platform cannot record that none did.

**Nothing in the file reveals that.** The sentence is coherent, well-argued, and describes a defect that no
longer exists — **and it would have sat directly above the code that depends on it being fixed.** A reader
would have concluded the discard was still live and read the surrounding code as wrong.

**Corrected to name the branch's framing, say why it no longer holds, and state what is actually left: a
FALSE REFUSAL**, where the write is turned away for a bookkeeping race the caller cannot see and could not
have avoided.
