## The check, and the sentence that keeps it honest

```
CHECKED : did any suite total move, when non-comment lines under src/ changed?
NOT     : do the tests the task required exist? do the tests that moved cover what was written?
```

**The gate does not know what a task required.** It can tell you that you changed code and no count
moved. **It cannot tell you the count that moved was the right one.** Every line it prints is worded
to claim only the first, because wording that implied more would convert an honest convention into a
false enforcement — and this repository has now recorded five instruments reporting on a domain
narrower than their wording implied.

## The demonstration that found a bug reading would not have

**Planting a real source change reported "no non-comment change under `src/`".**

```
################ 3. A REAL src/ CHANGE, NO NEW TEST ################
  --- condition 4: ok: no non-comment change under src/; 7 suite total(s) checked
```

`git diff` **does not report untracked files**, and a brand-new `.cs` file is the commonest form of
new code there is. So the check was blind to exactly the case it exists for — **the permissive,
silent-skip failure it was built to avoid, occurring inside itself.**

```
tracked diff lines  : 0
untracked lines     : 2      <- invisible before the fix
total the check sees: 2
```

**The line that was wrong is the line that looks right.** `git diff <base> -- src/` reads as the
obviously correct thing to write. It took planting a file to find out otherwise, which is why the task
said *demonstrated*, and the header records how it was found rather than only what it now does.

**The red run says it did not update.** A red run that silently leaves the baseline alone is

## Where the baseline lives, and why the instrument writes it

```
# Written by scripts/gate.sh on a green run. Do not hand-edit -- see note 7t.
# suite|configuration|total
API|Debug|724
Architecture|Debug|509
...
```

**A baseline a person maintains is a baseline nobody maintains.** The gate writes it, the coder commits
it, and the delta lands in the diff where review sees a count change as a reviewable line rather than
as a number in a log.

**It can be hand-edited, and the defence is visibility rather than prevention** — the edit lands next
to the code it excuses. That is the design, not a hole in it, and the header says so because someone
will otherwise report it as one.

Three properties that are not obvious:

- **Written once, after the last configuration, after the verdict.** Not "after the suites": under
  `PHASE` that is ambiguous, and a write between Debug and Release dirties the tree **while Release is
  reading it** — `DEC-L-013` with the gate doing it to itself.
- **Rows this run did not produce are carried forward.** A `TASK` run covers seven suites in Debug;
  dropping the rest would report Integration as having vanished on the next `PHASE`.
- **`Total:` rather than `Passed:`** — a skipped test still exists, and the question is whether the
  tests moved, not whether they ran.

## The measurement, and the granularity that is the finding

```
per merged PR (200):  45 touched src/ -- 44 added a new [Fact]/[Theory], 1 did not
per commit    (300): 126 touched src/ -- 19 added no test
```

**The gate runs once per task, and a task is several commits** — intermediate ones legitimately land
code before their tests. **Measure this per commit and you conclude it is unshippable.**

The single spurious fire in 200 merges was `#66 T-018`: nineteen added lines under `src/`, **all of
them a comment block, zero non-comment lines.** That is what the comment filter removes, and it is
exactly the *"a docs task, a rename"* case.

## Why it warns — and it is not the number

`0 in 200` is **evidence about this repository's past, not about the check**, and it is the same shape
as condition 1 having never been violated, which is what made that one look enforced when nothing
enforced it.

**The reason is the remedy asymmetry.** Conditions 0, 1 and 2 go red with an unambiguous fix. This
one's wrong-fire remedies are to **write a test you do not believe in, or route around the gate** — and
a red answerable by manufacturing a test produces exactly the tests that make a suite worthless. A
refactor covered by existing tests is *correct work* the gate would be asking to fake something for.
**That reason will still be true when the 200-merge number is stale.**

No assertion variable, ruled: the honest reason would be *"I refactored and existing tests cover it"*,
which is what a warning already permits without teaching anyone the bar is negotiable.
