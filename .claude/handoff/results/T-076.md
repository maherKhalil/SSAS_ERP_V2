## 1. Mounting and entitlement — `REQ-SS-0008` is TRUE, not merely intended

**A new route inside an existing group inherits four things for free**, because they are applied to the
group (`AttendanceEndpointRouteBuilderExtensions.cs:53-68`):

```
.WithTags("Attendance")
.RequireModule(AttendanceModuleEnablement.Key)          the BR-PLT-0008 gate + its metadata
.AddEndpointFilter<AttendanceCompanyContextEndpointFilter>()
.AddEndpointFilter(... ApiResponseSecurity.Apply ...)   response security headers
```

**And the design says so on purpose.** `ModuleEnablement.cs:86-89`: *"Applied to the GROUP, never to a
route. That is the whole point — a route added to an existing group later cannot forget the gate...
`RequirePermission` is per-route because permissions differ per operation; entitlement does not."*

**Two things must be declared per route:** `.RequirePermission(<name>)` and `.WithName(<id>)`.

**So a self-service route genuinely is an ordinary module route.** It needs no new gate, no new filter
and no new mounting: `endpoints.RequireModuleEnablementServices(...)` at `:50` is already called, and
the group already exists. **`REQ-SS-0008` is a statement about the tree and it holds.**

*(Aside worth having: the entitlement resolver currently grants everything —
`ModuleEnablement.cs:13-16` states plainly that `BR-PLT-0008` is **not yet satisfied** because no
subscription data exists. The seam is real; the answer is presently always yes.)*

## 2. Is `AC-SS-0007` assertable against the contract?

# **YES — for all four surfaces, and each already has a working precedent in this suite.**

| Surface | Mechanism | Precedent |
|---|---|---|
| **body** | reflection over the module's `*Request` records | `AttendanceTransportContractTests.cs:31-36` |
| **path** | `RouteEndpoint.RoutePattern`, exposed by `MappedRoutes()` | `PayrollRouteInventoryTests.cs:42-56` |
| **query / header** | `endpoint.Metadata.GetMetadata<MethodInfo>()` → handler parameters | `ModuleEnablementCoverageTests.cs:50` |

**The body half is the strongest and it is already in Attendance.** `AttendanceTransportContractTests`
derives its type set rather than listing it — *"A request record added later is covered without anybody
remembering to add it here"* — and it carries its own non-vacuity assertion
(`There_are_request_records_to_check_so_this_guard_is_not_vacuous`, `:38-45`) for exactly the reason
this file keeps rediscovering.

**The query/header half is the one I expected to be unreachable and is not.** Minimal-API handler
parameters are not visible on the route pattern, but the handler's `MethodInfo` is in endpoint
metadata and **this suite already reads it** — `ModuleEnablementCoverageTests.cs:50` uses
`endpoint.Metadata.GetMetadata<MethodInfo>()?.DeclaringType?.Assembly` to attribute an endpoint to a
module. The same handle reaches `GetParameters()` and their `[FromQuery]` / `[FromHeader]` attributes.

**So the criterion was written on a possible assumption.** It is assertable against the contract and
the endpoint, without invoking a handler.

## 3. How a handler obtains the caller — and when it is null

```
ICurrentTenantUser.TenantUserId          CurrentTenantUser.cs:17-18   long?
  <- ICurrentAuthenticationSession.Value  CurrentAuthenticationSessionAccessor.cs:11-31
  <- the request principal's claims
```

**`Value` is null unless ALL of the following hold** (`:16-30`), and any one failing yields null rather
than an exception:

```
principal.Identity.IsAuthenticated                                  is true
IdentityId, TenantUserId, SessionId, SecurityVersion                each a positive Int64 in CANONICAL form
TenantId                                                            a canonical "D"-format Guid, non-empty
ClientId                                                            AuthenticationClientId.Create succeeds
```

*Canonical form is asserted, not just parsed* (`:34-36`): the round-tripped string must equal the claim
ordinally, so `007` fails where `7` succeeds.

**The absence is deliberately a null and not a throw** — `CurrentTenantUser.cs:12-14`: *"Background and
maintenance compositions legitimately have none, and the boundary that requires an acting user is the
one that refuses — not this accessor."*

### The distinction `REQ-SS-0005` turns on, and it is not the one the accessor makes

**`TenantUserId == null` means "there is no tenant session at all"** — unauthenticated, a platform-plane
token, or a background composition. **It does not and cannot mean "this identity has no employee
record."**

A tenant-authenticated caller **always** has a `TenantUserId`. The unmapped case is a *lookup miss* in
the mapping — a tenant user that exists, with no linked employee. **Those are two different refusals
with two different causes**, and only the second is `REQ-SS-0005`'s ordinary-refusal case. The first is
an ordinary 401/403 that never reaches a handler.

## 4. What an ordinary refusal looks like — and the default is a 5xx

**The shape exists and a handler produces it without throwing.**

```
handler          return Problem(context, result.Error)     AttendanceEndpointRouteBuilderExtensions.cs:142-143
maps via         AttendanceApiErrorMapper.Map(Error)  ->   ApiError(StatusCode, Code)
projects via     ApiProblems.Problem(context, error, resourceKey)   ApiProblems.cs:43-59
                 -> Results.Problem(type, statusCode, title, extensions{code, correlationId, resourceKey})
```

**`Results.Problem` returns an `IResult`. Nothing is thrown, and no logger is touched on this path.**
So `AC-SS-0008`/`AC-SS-0009`'s *no exception, no error-log entry* is satisfied by the existing shape.

# **But the *no 5xx* half is not free, and this is the finding.**

```
AttendanceApiErrorMapper.cs:149     _ => ApiErrors.WriteFailure
ApiErrors.cs:32                     WriteFailure = new(500, "request.failed")
```

**An unmapped error becomes a 500.** A handler returning `Result.Failure(new Error("Attendance.NoEmployeeForIdentity", ...))`
throws nothing, logs nothing, and **answers `500 request.failed`** until someone adds a line to the
mapper.

**And nothing forces that line.** I searched for a guard asserting every module error has a mapping
other than the fallback and **found none**. So the failure mode is: the handler is correct, the domain
error is correct, no exception occurs — and the criterion is violated by an omission that is invisible
in a diff of the handler.

**That is the same shape as FP-006P and FP-011**: an absence, in a second file, that leaves the first
file looking right.

## 5. What adding a route costs in the inventory — and the two halves differ starkly

### Payroll — three places, all of which fail loudly

```
PayrollRouteInventoryTests.cs:14-40   the Expected (Method, Pattern, Permission) list
              :42-56  the route surface is EXACTLY the documented inventory   -> RED on an unlisted route
              :60-70  every payroll route requires a permission               -> RED on an unprotected one
              :74-84  every route requires the permission the inventory names -> RED on a mismatch
```

### Attendance — nothing. There is no inventory and no route test at all

```
tests/API.Tests/Attendance/          contains exactly one file: AttendanceTransportContractTests.cs
grep -rn "api/attendance" tests/     ZERO matches across the whole test tree
```

**HR, GL and Payroll each have `Every_<module>_route_requires_a_permission`
(`HrRouteInventoryTests.cs:52`, `GlRouteInventoryTests.cs:60`, `PayrollRouteInventoryTests.cs:60`).
Attendance has no equivalent, and no test anywhere exercises an Attendance route.**

**So an Attendance route added with no `RequirePermission` would be reachable by any caller and nothing
would fail.** There is **no fallback authorization policy** — the `RequireAuthenticatedUser()` at
`PermissionAuthorizationPolicyProvider.cs:75` is inside `CreatePolicyBuilder()`, which builds *named*
policies; it is not `AuthorizationOptions.FallbackPolicy`. An endpoint with no authorization metadata
is anonymous.

**What a new Attendance route IS covered by** — the cross-cutting guards, which are module-agnostic:

```
ModuleEnablementCoverageTests.cs:74,96   gated, and declares its own module key   (all four modules)
EndpointPermissionCatalogJoinTests       the permission is catalog-defined         (T-072, all modules)
                                         the plane matches the permission's scope  (T-073, all modules)
                                         every endpoint is classified              (T-072)
```

**Note what that set does *not* include: "requires a permission at all."** My T-072 accounting test
classifies a permission-less route into the *anonymous* bucket, and the three-bucket identity still
balances — **so it stays green.** The gap is real and I own the guard that comes closest to it without
closing it.
