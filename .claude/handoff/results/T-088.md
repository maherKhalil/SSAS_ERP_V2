# THREE GUARDS FIRED, AND EACH ONE WAS THE POINT

**None of them was an obstacle. Each forced a decision through a person that would otherwise have been made
by whoever typed fastest.**

## 1. DI validation — the coupling I could not see by reading

`ResolveForOwnEmployeeAsync` began as a method on `IPayrollScopeResolver`. **Twenty-five API tests failed
DI validation**, and the message named every handler the coupling reached:

```
Unable to resolve 'IUserEmployeeResolver' while activating 'PayrollScopeResolver'
  ... validating CreatePayElementCommandHandler, RecordCompensationCommandHandler,
      Generate/Create/Calculate/Approve/Post/ReversePayrollRunCommandHandler
```

**A self-service concern had become a construction-time dependency of every payroll write.** Split into
`IPayrollSelfServiceScopeResolver`; `IPayrollScopeResolver` is restored **byte-identical** to pre-T-088.

**I learned it was shared machinery by breaking it.** A design review would have missed it — the container
did not.

## 2. The employee-set door list — and the dodge I turned down

`EmployeeCompanyDirectoryService` is a **fourth** file touching `Set<Employee>()`, and **the first with no
company authorization at all** — which is precisely the property that guard exists to police, removed by
ruling rather than lost.

**The dodge was available and cheap:** put `GetCompanyIdAsync` on `EmployeeRosterService`, an
already-sanctioned file. The guard checks file names, so it would have gone green — **with an unlocked read
hidden inside a locked file, and the guard still passing while the property it protects was gone.**

**Admitted by ruling instead, with the lock named in the guard's own terms:** tenant isolation, **plus an
identifier that is never caller-supplied.**

### And the second half of that lock is now asserted, because it was prose

**`Only_the_self_service_scope_resolver_injects_the_company_directory`** enumerates constructors across every
assembly that references `HR.Contracts` and pins the injection set to exactly one type.

**That lock lived entirely in who calls it.** A second injection site could pass any employee identifier and
face no company check — the door list's property arriving through a caller instead of a file. **Now a second
caller requires a person, exactly as a fourth door did.** `DEC-L-072`, applied on the day the door opened.

## `AC-SS-0007` — the first test in the tree to inspect handler parameters

**The line it draws is inherited by everyone after it, so the classification is reported rather than
assumed.** A minimal-API handler's parameters mix values **bound from the request** with **services**; only
the first is a contract member, and a sweep treating an injected `IPayrollReadService` as one would be
asserting nonsense.

**The unrecognised case is treated as bound, not excused** — the conservative direction — and the failure
message prints both lists so a future reader can dispute which side a parameter landed on instead of
deducing the rule from a comment.

## The dangling link, answered as ruled

A link outliving the employee it names **is reachable** — `ADR-030` Decision 4 forbids the foreign key that
would prevent it — and **collapses into the same 404.** The caller cannot act on the difference, and
distinguishing it would disclose that a link exists pointing at a record that does not.

**The cost is named in the resolver rather than buried: a dangling link is invisible from the wire**, and
detecting one belongs to whoever owns the link's lifecycle, not to a read.
