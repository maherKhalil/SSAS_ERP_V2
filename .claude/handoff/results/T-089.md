# THE THREE DECISIONS WORTH A PERSON'S ATTENTION

## 1. `TS-SS-0003` was generalised, and the alternative was a per-route exception

T-088 wrote the criterion as **`bound.Count == 0`** — the self payslip route binds nothing, so "nothing
bound" and "no subject bound" were the same assertion and the stricter one was cheaper.

**`/api/attendance/me/records` legitimately binds `fromDate` and `toDate`.** A date range narrows a set the
caller is already authorized to see; it cannot widen one.

**The cheap path was to exempt this route.** That is how a guard stops meaning anything — the next route
inherits the exemption as precedent, and nobody re-derives why it was granted.

Instead the rule now states the property it always meant, in `tests/API.Tests/Infrastructure/SelfServiceContractRule.cs`:

- **BY TYPE** — a bound `Guid`/`long` (and nullable forms) is refused. Catches `Guid? employeeId` renamed
  to `subject`, `forWhom`, `id`.
- **BY NAME** — a bound parameter naming a person is refused whatever its type. Catches `string employeeCode`.

**One place, two modules.** Payroll's test now calls the same helper, so the two cannot drift into two
different definitions of one criterion (`DEC-L-072`).

## 2. The Own/Self/Mine guard became an inventory instead of being deleted

It asserted that **no** permission name contains `Own`, `Self` or `Mine`. FP-015 makes that false.

**The question it answered was never "is there a self permission".** It was *"has a self-service surface
appeared without a person deciding its shape"* — and **an absence check answers that exactly once, then gets
deleted and answers nothing ever again.**

Now an exact set of two. **A third still costs a person a conversation**, which is the whole property.

## 3. `maySeeSensitive: true` on the self leave route — A RULING I MADE, AND THE ONE TO OVERTURN IF ANY

`REQ-ATT-0025` redacts a sensitive leave TYPE because it identifies an individual's medical absence.

**The party it protects is the subject, and on this route the subject IS the caller.** The gating permission
is `Attendance.Leave.ViewSensitive`, an administrative grant no plain employee holds — so applying the
administrative rule here would make the redaction *universal* on this route, not conditional, and an employee
could not see which of their own leave they took. Sick leave would render as a nameless gap.

**T-088's precedent points the same way:** an own payslip is returned in full, and a payslip discloses at
least as much about a person as a leave type does.

**Cost named rather than hidden, in the read service:** this route shows the caller their own sensitive leave
type on a screen that can be shoulder-surfed. Same exposure as their own payslip.

**If you disagree, the change is one argument at one call site** — `AttendanceReadService.GetLeaveRequestsForEmployeeAsync`.

## Two scope methods, and why one would have been a live defect

Attendance's read scope has three dimensions and its two surfaces use different ones: **records are
branch-scoped** (`AttendanceReadService.cs:105`, `OD-ATT-0011`) and **leave is company-only** (`:179`, `:233`).

A single `ResolveForOwnAsync` returning "a scope" would let the records path receive a company-only scope and
filter on the sentinel branch nobody set — **a silently unbranched read that looks like a working feature**.
The two positive tests assert the branch set both ways: `[BranchId]` for records, `[Guid.Empty]` for leave.

## The two self reads share their query with the administrative one

`GetRecordsAsync` and `GetRecordsForEmployeeAsync` both run `QueryRecordsAsync`; the leave pair likewise.
**One query per surface, so the branch predicate cannot hold on one path and go missing on the other.**

The difference is only where the scope comes from: the administrative entry resolves an administrative
permission, the self entry is handed a scope built from the caller's own employee. **The factory stays
`internal`, so a handed-in scope is still proof that live resolution ran** — what a caller cannot do is forge
one.

## Attendance's first transport harness

T-076 measured that no test anywhere called an Attendance route; T-077 proved by planting one that the whole
suite stayed green. `AttendanceRoutePermissionTests` closed the metadata-visible half.

**FP-015 adds a surface whose correctness is not visible in metadata** — which employee a read resolves to,
which dimensions its scope carries — so `AttendanceApiTestHost` answers real requests. It registers what the
self routes need and nothing else, and **the scope resolver in it is real**; only its two doors out of the
module are stubbed. A stubbed resolver would leave the tests asserting that a fake returns what it was told.

## For the architect

### Two documents to write — proposed wording, NOT written, as instructed

**`AC-ATT-0032`** currently reads as an absence criterion ("no self-service permission is declared"). Proposed:

> **AC-ATT-0032** — The Attendance module declares exactly two self-service permissions,
> `Attendance.Records.ViewOwn` and `Attendance.Leave.ViewOwn`. Neither grants the other, and neither is
> granted by any administrative Attendance permission. A third self-service permission requires a recorded
> decision.

**`REQ-ATT-0023`** — proposed:

> **REQ-ATT-0023** — An employee holding `Attendance.Records.ViewOwn` may read their own attendance records,
> scoped to their own company and their own branch. An employee holding `Attendance.Leave.ViewOwn` may read
> their own leave requests, scoped to their own company. In both cases the subject is resolved from the
> authenticated identity via `UserEmployeeLink` and never from the request. A caller with no linked employee
> is answered `404 attendance.no_linked_employee`.

The test file already carries the `TS-SS-0013` / `AC-SS-0005` / `AC-SS-0007` / `AC-SS-0008` traits, so the
matrix rows exist as soon as the criteria are written.
