# ESTABLISHED FIRST — QUESTION 1, AND THE ANSWER IS "YES, BUT"

**FP-013's package DOES document its routes**, so the inventory has something to compare against. But not
in the shape the other packages use, and not currently:

- it is a **code block, not a table**, so a search for the table shape finds nothing;
- the document is titled **"API contracts (proposed)"**;
- and it diverges from the live surface in **six places**.

**None of the six is a permission disagreement** — every route present in both documents the permission the
code requires. The divergences are all about *which routes exist*.

```
DOCUMENTED, NOT LIVE
  GET   /api/attendance/calendars/{id}/working-days      live path has NO id
  PUT   /api/attendance/leave-balances/{id}              live path has NO id
  POST  /api/attendance/records/bulk                     never built

LIVE, NOT DOCUMENTED
  GET   /api/attendance/calendars/working-days           the other half of the first divergence

  POST  /api/attendance/records/{id}/adjustments         OD-ATT-0012's correction route
```

**So: two path divergences, one documented-and-never-built, three live-and-never-documented.**

**Reported, not fixed** — the constraint was explicit, and two of the six are not clerical. `POST
/records/bulk` may be a route somebody still intends; the two path divergences are a choice about whether
the id belongs in the path, which is a contract decision.

## Why the inventory is NOT asserted against that document

**The three existing inventories carry their expected set in the TEST, not in the package document**, and
this one follows them. That is the pattern's own answer to the question the constraint raises: the test is
the assertable inventory, and the document is prose that can be corrected separately.

**Writing the document to match the code would have been the shortcut warned about** — and worse here,
because it would have silently retired `POST /records/bulk` by deleting it from the only place it is
recorded.

## Which of the three I followed, and why

**`PayrollRouteInventoryTests`.**

- **It is the only one whose three properties are three separately NAMED tests.** A failure says *which*
  property broke rather than "the inventory differs". HR's folds the permission check into a 213-line file;
  GL's is close but thinner.
- **And its self-service row carries the reason inline**, which is exactly what Attendance needed: the two
  `/me/` routes carry SELF permissions that share a prefix with the administrative ones and nothing else.

**The "every route requires a permission" half is not repeated.** T-077 built it for Attendance against the
same enumeration, and the architect's instruction was to reference rather than duplicate — a second copy is
two places to edit and one place to forget.

## Question 2 — the two in-handler permissions, handled explicitly

`Attendance.Leave.ViewSensitive` and `Attendance.Leave.ApproveAtRoot` are declared, catalogued and required
by no route. An inventory keyed on route-to-permission **would imply they are missing.**

`The_two_permissions_enforced_in_a_handler_are_named_rather_than_missing` asserts two things:

1. **Neither is any route's permission** — the claim the test is making. If one ever becomes route-gated,
   this fails and the entry has to go; the two lists cannot both be right.
2. **Both ARE catalogued.** A permission no catalog defines refuses every caller (FP-006P); one enforced in
   a handler and never catalogued would be worse — **it would refuse silently, inside a response.**

**The reason is stated rather than assumed:** a route gate can only refuse a *whole request*, and both of
these are decisions about **part** of a response (`ViewSensitive` redacts a leave type per row) or **part**
of a flow (`ApproveAtRoot` gates approval once a request has reached the root).
