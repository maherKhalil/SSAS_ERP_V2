# T-191 (item 40) — tests that cannot prove the guard they name

**Enumerate and rank. Nothing planted, nothing fixed.**

Ranking criterion, as widened after the fiscal-year lock: **a test cannot prove a guard it
never triggers.** The test-host stub is its commonest cause, not its definition — the lock
case had real SQL Server, a real repository and the real registration, and was still blind,
because the *condition* the code guards against was one no test ever created.

Instruments: `stub_survey.py`, `rank_blind.py`, `rank_oracle.py`. Each refuses rather than
reporting zero if its scan degrades, because every count here is one an empty result would
silently flatter.

## Count first

Tier 2 is a list, not a ranking, and most of it is legitimate: a test named for a repository
that asserts an endpoint's status code is correct as it stands. **Tier 3 is the actionable
set**, and tier 1 ∩ tier 3 is where the name outruns the evidence.

## The distinction that does the ranking

Reading the 99, the split is not subtle and it is almost entirely visible in the **name**:

- `Database_unique_violation_on_save_maps_to_409_company_code_conflict` — says **maps to**.
  That is exactly what it proves. **Correctly named, no action.**
- `A_duplicate_account_code_race_is_409_rather_than_500` — says **race**. No race occurs; the
  test sets `host.UnitOfWork.Failure` and asserts the mapping. **The mapping half is proven
  and the race half is not.**

So most of this set needs a **rename, not a new test** — the coverage is real, the claim is
too wide. That is cheap, and it is the difference between a suite that is honest about its
reach and one that reads as covering concurrency it has never exercised.

## The ranked list

**1 — `IDepartmentHierarchyLock` has no behavioural evidence at all. ⚠ LOAD-BEARING.**
`DepartmentAppFixture` composes the real `SqlServerDepartmentHierarchyLock` on a real
connection; `DepartmentApplicationSqlServerTests` never opens a second one. The API host
registers `GrantingHierarchyLock`, which grants unconditionally. The architecture tests check
the interface's *shape*. **This is precisely the state GL's fiscal-year lock was in before
T-190** — and the same plant (grant unconditionally, never call `sp_getapplock`) would go
unnoticed. The remedy already exists and is a transposition of
`GlFiscalYearDefinitionLockContentionSqlServerTests`, including the refuses-everyone control.

**2 — `A_busy_fiscal_calendar_is_409_and_names_a_retryable_condition`** (`Gl/GlEndpointTests`,
sets `host.CalendarLock.Failure`). The name claims the calendar was *busy*, a lock outcome.
It proves the mapper turns `CalendarDefinitionBusy` into a 409 and names it retryable — worth
having, and correct. It proves nothing about busyness ever arising. Now partly redeemed by
T-190; **rename to name the mapping.**

**3–7 — the five `_race_is_409_rather_than_500` tests.** `A_duplicate_account_code_race`,
`A_duplicate_fiscal_year_code_race` (Gl), `A_duplicate_pay_element_code_race`,
`A_duplicate_payroll_period_race`, `A_duplicate_payroll_run_race` (Payroll). All set
`host.UnitOfWork.Failure`. All prove the persistence-failure→409 mapping and none proves a
race. **Rename.** The underlying concurrency, where it matters, is a database uniqueness
constraint and is proven in Integration.

**8–10 — the constraint-named department tests.**
`D23_A_unique_constraint_on_assign_manager_is_a_concurrency_conflict`,
`D24_A_rowversion_conflict_on_assign_manager_answers_identically`,
`D6_A_unique_constraint_on_create_is_a_code_conflict`. Same shape, same remedy. D24 is the
most over-claimed of the three: no rowversion is ever compared.

**11 — `An_ambiguous_calendar_refuses_rather_than_falling_through_as_open`** (Payroll, sets
`host.Ledger.Window`). Already found and already answered in T-188 — it proves the two
consumers, and `PostingWindowAmbiguityTests` was added for the emitter. **Listed because the
sweep must find the case that motivated it**; an instrument that cannot rediscover its own
founding example is not calibrated.

**12 — `A_ledger_refusal_at_posting_refuses_the_transition`** (Payroll, sets
`host.Ledger.PostOutcome`). Honest as it stands: its subject *is* the payroll transition's
response to a refusal, and the ledger is legitimately someone else's unit. **No action —
included as the boundary case that shows where the list stops.**

## What I did not do, and why

No plants. Ranking cost nothing to run; a plant per test is the expensive half, and on this
evidence most of the 99 would come back "correctly scoped, badly named", which a rename fixes
without a plant.

## My judgement on what should follow

**Do #1 and stop.** It is the only entry that is a missing *guarantee* rather than a wide
*claim* — a lock in production with no evidence it is ever acquired, in the module that
manages the department hierarchy every other module reads through. Everything from #2 down is
a naming correction, and those are better done as one sweep when someone is already in the
file than as a task of their own.

⚠ **And the general form deserves recording somewhere the next reader will hit it:** two locks
were written, both were composed for real in Integration, and neither was ever contended.
That is not two mistakes. It is one missing habit — **a lock's test must include a second
connection, or it is testing that the lock does not crash.**
