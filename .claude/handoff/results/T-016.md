## ⚠ TWO PREMISE CORRECTIONS — the task was written against a misdiagnosis I supplied

### 1. The abort path was never broken

**All four preconditions already exit non-zero and always did.** Proven by running it, not by reading:

```
$ GATE_MODE=LEAN GATE_MEMORY_FLOOR_MB=999999 bash scripts/gate.sh
########## GATE MODE: LEAN (floor 999999 MB, ceiling: -- xUnit.MaxParallelThreads=4)
########## Debug ##########

!!! On 2026-08-24 both Integration legs died with no TRX at 14 MB and 92 MB free.

```

`exit` inside `reap_to_zero` terminates the **script**, because the function is called plainly from
the `for CFG` loop — never in a subshell, never behind a pipe. Codes: `2` testhost running,
`3` protected catalog, `4` reap left catalogs, `5` below the memory floor.

### 2. What returned 0 was my invocation

The identical run, piped:

```
$ GATE_MODE=LEAN GATE_MEMORY_FLOOR_MB=999999 bash scripts/gate.sh | tail -3
!!! ABORT (Debug): PRECONDITION FAILURE -- only 1580 MB free, floor is 999999 MB.
...
exit: 0
```

**A shell pipeline yields the status of its last command, and `tail` succeeded.** The same pipe also
buffered stdout, which is why a 69-minute run showed nothing. I reported both as defects in this
script. **Neither was.** The `tail` habit is on the board already and the spec correctly scoped it
out — but it is the root cause of the premise, so it belongs at the top of this report.

## ✅ But auditing for the bug that did not exist found a worse one that did

**The script had no terminal `exit`.** It printed `[GATE RED]` or `[GATE GREEN]`, then
`[GATE COMPLETE]`, and fell off its own end — and a bash script ending without `exit` returns the
status of its last command, which was that `echo`.

**So a red gate exited 0.** `GATE_FAILED` was computed correctly at line 361 and then discarded.

```
$ ( GATE_FAILED=1; if [ $GATE_FAILED -ne 0 ]; then echo "[GATE RED]"; else echo "[GATE GREEN]"; fi
    echo "[GATE COMPLETE -- ...]" )
[GATE RED]
[GATE COMPLETE -- ...]
exit: 0        <-- a RED gate reporting success
```

**This is the same failure the task was written about, reached from the other direction** — not a
status swallowed by a pipe, but a status never set. And it sat on **the one path that matters most**:
`DEC-L-007` makes a green gate the merge authority for code, so a gate whose *suites failed* reported
success to anything reading `$?`. The abort paths the task targeted were the safe ones; the failure
path was not.

Fixed with an explicit `exit $GATE_FAILED`, verified by exercising **the real terminal lines** of the
edited script both ways:

```
--- extracted from the script:
exit $GATE_FAILED

--- RED path:    exit: 1
--- GREEN path:  exit: 0
```

`1` is distinct from the precondition codes on purpose: **2–5 mean the run never started, 1 means it
ran and something failed.** A caller can tell "the box was not ready" from "the code is broken",
which is the distinction the whole precondition apparatus exists to preserve.
