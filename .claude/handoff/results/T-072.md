## What it asserts

`tests/API.Tests/Infrastructure/EndpointPermissionCatalogJoinTests.cs`, two facts:

1. **`Every_permission_an_endpoint_requires_is_defined_by_the_composed_catalog`** — the join.
2. **`Every_endpoint_is_classified_and_no_policy_escapes_the_join`** — the accounting.

Both enumerate from `HostWebApplicationFactory`, which wraps the real `Program`. **Measured, not
assumed:** the production composition yields **147 route endpoints, 64 distinct policies and a
composed catalog of 85 permissions**, spanning Attendance, GL, HR, Payroll and Platform.

**Permission names are recovered with `PermissionAuthorizationDefaults.TryGetPermissionName` and its
platform-plane twin** — the inverse of the `CreatePolicyName` that built the policies, so recovery is

**No list of endpoints and no endpoint count.** A hand-written expected list would be the third
document that can agree with the other two while all three disagree with the catalog — the defect

## The skips are accounted for, not filtered away

**Four endpoints carry `.RequireAuthorization()` with no policy** — any authenticated caller reaches
them, and the join cannot examine them:

```
GET  /api/platform/localization/effective/
POST /api/platform/localization/effective/batch
POST /api/platform/auth/logout
POST /api/platform/support/auth/logout
```

**All four are deliberate, verified at their map sites** (`LocalizationEndpointRouteBuilderExtensions.cs:51-52`,
`AuthenticationEndpointRouteBuilderExtensions.cs:30`, `PlatformSupportAuthenticationEndpointRouteBuilderExtensions.cs:52-53`).
Logging out must not require a permission or a user could be stranded holding a session they cannot
end; effective localization is the UI's own strings, needed before a caller holds any permission.

**They are pinned by name, and that is the only list in the file.** A count passes when one is removed
and another added. Naming means a **fifth** authenticated-only route has to be acknowledged by
someone who writes down why it is not permission-bearing — the one way a route can leave the join
unnoticed, and therefore the one place a hand-written list belongs.

**The accounting identity is the report a passing test can make:**

```
anonymous (9) + policy-bearing (134) + authenticated-only (4) == 147 endpoints
```

Three buckets summing to the whole. **Nothing is skipped silently, because nothing is skipped at all**
— every endpoint changes one of the three. And the residual policy bucket (a policy that is neither
tenant nor platform permission) is asserted **empty**: a future policy shape must be classified here
rather than quietly falling outside the join. It is empty today; there are **no role policies on any
mapped route.**

**The join asserts non-empty before it loops.** A filter that matches nothing produces a green loop
over an empty set — a guard that cannot fail, which this repository has produced twice. If the policy
spelling changes and recovery stops matching, that line fails rather than the suite quietly passing.

## The grammar divergence — my reading, as a recommendation and not a change

**Recommendation: do not narrow `AuthorizationNameValidator`. I would leave it exactly as it is.**

Two reasons, the second of which I did not expect and which I think is decisive.

**1. The join already catches the consequence.** A four-segment policy IS recovered as a permission
name — `TryGetPermissionName` uses the lax validator — and then fails `catalog.TryGet`, so the join
goes red naming the route. **The divergence is now caught rather than fatal, which may be the entire
answer**, as you suggested it might be.

**2. The validator is shared with role names, and role names have no segment rule at all.**

```
RoleAuthorizationDefaults.cs:36   IsValidRoleName -> AuthorizationNameValidator.IsValid
RoleName.cs:17-23                 Create: non-blank, <= 100 characters. NO segment rule whatsoever.
```

Role names are tenant-authored. **Narrowing the shared validator to three segments would break role
policies**, and it would do so in the direction of a domain type that deliberately imposes no
structure. The two name kinds already disagree with each other more than permissions disagree with
themselves.

**If anything is warranted it is a permission-side validator that is not shared with roles** — but
that is a distinct decision about a second type, with its own blast radius, and I have not made it.
`PermissionAuthorizationTests.cs:21` constructs `new PermissionRequirement("test.permission")` — two
segments — so existing tests depend on the current laxity, which is worth knowing before anyone
touches it.

## What this does not cover, named

- **Scope correctness is not asserted.** A tenant-prefixed route requiring a `PlatformSupport`
  permission is catalog-defined and passes the join, but `TenantPermissionClaimFilter.cs:27-28` drops
  that permission from tenant tokens, so the route is unsatisfiable — **the same class of defect,
  caught by neither guard.** I left it out because the task asked for the join and widening it was not
  mine to decide. **I think it is worth a follow-up and it is cheap**: the catalog already carries the
  scope, and the policy prefix already declares the plane.
- **Policy strings are sometimes hand-spelled.** `LocalizationEndpointRouteBuilderExtensions.cs:39-48`
  writes `$"Permission:{...}"` by interpolation rather than calling `CreatePolicyName`, so it bypasses
  that method's validation entirely. It happens to be correct. **The join covers the consequence
  regardless of how the string was built**, which is an argument for the join sitting where it does.
- **Module enablement.** The guard sees what the Host maps in Development. If a module were disabled
  and its routes unmapped, they would not be examined. I did not establish whether any configuration
  disables a module's routes at startup.
