# 1. NO, AN ASSIGNMENT CANNOT BE BOUNDED — AND THE REASON IS WORSE THAN RECURRENCE

```
PayElementAssignment          EmployeeCompensationId, PayElementId, RateOrAmount
                              no dates, no period, no consumed flag
```

**Confirmed: it recurs in every period its parent compensation record is in force.**

**But the decisive fact is entanglement, not recurrence.** The assignment hangs off `EmployeeCompensation`,
**and that same record carries `BaseAmount`** — so *you cannot add a one-off payment without restating the
employee's base salary*. A one-off would arrive as a new compensation record, which is a new answer to
*"what is this person paid"*, permanently, in the history `DEC-POS-0023` exists to keep honest.

**And bounding it is a knife-edge.** `InForceOn(history, period.PayDateUtc)` selects on the **pay date** — a
single instant. Stopping a one-off by writing a superseding record means landing two records either side of
one timestamp, and whether the payment happens depends on which one wins.

**So this is code, not configuration.** Your *"if an assignment CAN be bounded then most of this task is
configuration"* resolves the other way, and it resolves on the aggregate rather than on preference.

# ⚠ 2. NO. A ONE-OFF-ONLY PERSON CANNOT BE PAID AT ALL TODAY

`PayrollRunCommandHandlers.cs:188-201` — **two skips:**

```csharp
if (!byEmployee.TryGetValue(record.EmployeeId, out var employeeHistory)) continue;   // no compensation
var inForce = EmployeeCompensation.InForceOn(employeeHistory, period.PayDateUtc);
if (inForce is null) continue;                                                       // none in force
```

**A contractor paid once for a job has no monthly, daily or hourly rate, so they have no compensation record,
so they are skipped entirely.** They do not appear on the run, produce no line, and generate no error.

**The comment there is right and is right about a different case:**

> *"An employee with no compensation on file is SKIPPED, not defaulted to zero. A zero-pay line would look
> like a decision somebody made; an absence is the truth."*

**That is correct for a salaried employee whose record is missing. It is exactly wrong for someone who was
never meant to have one** — and the code cannot tell the two apart, because nothing in the model says which
this person is.

## And the payee must be an HR Employee, which bounds this task

```
roster.GetEmploymentAsync(...)                      // HR's fact, through HR's contract
period.Includes(employee.HiredUtc, employee.TerminatedUtc)
```

**Payroll pays people who appear in HR's employment roster with employment dates.** A person who is not an
employee at all cannot be paid by any mechanism here.

**So T-110's payee is an Employee with employment dates covering the period** — and *"pay someone who is not
an employee"* is the employment-type question the owner reserved. **Naming it so the boundary is deliberate.**

# 3. RECOMMENDATION — A REFERENCE TO THE APPROVED RUN, CONSUMED AT APPROVAL

## Not at calculation, because calculation is repeatable BY DESIGN

```
SetCalculation refuses only Approved and Posted   ->   Draft and Calculated are recalculable
```

**A one-off consumed at calculation would be consumed by a draft that may be recalculated or abandoned.**
Approval is already the sensitive, once-only act (`BR-PLT-0103`, `OD-PAY-0009`) and the promotion boundary.

**So: the instruction is INCLUDED whenever it is unconsumed and the period matches; APPROVAL is what
consumes it.** A re-run before approval re-includes it and produces the same line — idempotent for free,
with no flag to reset.

## A run REFERENCE, not a boolean

- **A bool says *that* it was paid and never *by what*.** Every payroll question about a payment is "which
  run" — reconciliation, reversal, a dispute.
- **It makes double payment structurally impossible rather than flag-guarded**: the instruction is either
  unconsumed or it names the run that paid it.

## And it does NOT import `EmployeeCompensation`'s argument, which is the trap you flagged

That aggregate refuses an end date because *"the end of one record is the start of the next"* — **an argument
about a CONTINUING value with a successor.** A one-off has no successor. **The field records an EVENT, not a
boundary**, so the refusal does not transfer and neither does its reasoning.

## ⚠ AND ONE THING I WILL NOT ANSWER — REVERSAL

`POST /runs/{payrollRunId}/reversals` exists. **Does reversing the run that paid a one-off make it payable
again?**

- **Yes** — the payment was undone, the obligation stands, and a reversal that left it consumed would strand
  it permanently with no path to pay.
- **No** — a reversal is a correcting entry, not an erasure, and re-arming it invites paying twice through
  two runs.

**Both defensible, and it is a ruling rather than a detail.** Whatever is chosen must be written where the
consumption is recorded.

# ⚠ AND ONE THE AGGREGATES FORCE THAT YOU DID NOT ANTICIPATE

**The run includes employees by PERIOD and selects their compensation by PAY DATE.**

```
inclusion     period.Includes(HiredUtc, TerminatedUtc)          <- the PERIOD
compensation  EmployeeCompensation.InForceOn(history, PayDateUtc) <- a single INSTANT after it
```

**Those are different questions and they can disagree** — an employee terminated inside the period is
included, and the compensation in force on a pay date *after* their termination is whatever the history says.
That asymmetry exists today and is not T-110's to fix.

**But it decides one thing here: a one-off must be scoped to the PERIOD, not the pay date.** Scoping it to
the pay date would inherit an inconsistency for a brand-new construct that has no reason to carry it.
