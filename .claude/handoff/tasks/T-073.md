# T-073 — Scope correctness: the permission a route requires must be satisfiable on that route's plane

**Your finding, at the end of T-072, and you were right not to widen the task to take it.**

## What you found

A tenant-prefixed route requiring a `PlatformSupport` permission **passes the T-072 join** — the
catalog defines the name, so the join is satisfied — and is nonetheless **unsatisfiable**, because
`TenantPermissionClaimFilter` drops that permission from every tenant token before it can become a
claim.

**Verified before issuing this, both halves:**

```
TenantPermissionClaimFilter.cs:27-28   !catalog.TryGet(name, out var d) || d.Scope == PermissionScope.Tenant
PermissionAuthorizationDefaults.cs:8   PolicyPrefix = PermissionPolicyNames.TenantPrefix
PermissionAuthorizationPolicyProvider.cs:14,19   two prefixes, dispatched on — the plane is IN the policy name
```

**So the two facts a check needs are both already present and neither is currently consulted against
the other:** the **policy prefix declares the plane**, and the **catalog records the scope**.

**This is the same class as T-072 and it is a step further in.** T-072 asks *does this name exist?*
This asks *can the caller this route is for ever hold it?* **Both failures look identical from the
outside — a correct-looking route that refuses everyone — and neither produces a red anything today.**

## Build it

**Extend the enumeration you already built. Same endpoints, same catalog, one more property:** for
every policy-bearing endpoint, the plane its policy prefix declares must match the scope the catalog
records for the permission it names.

**Both directions are defects and I want both asserted:**

- **Tenant-prefixed policy on a `PlatformSupport` permission** — the claim never reaches the token.
- **Platform-prefixed policy on a `Tenant` permission** — `PlatformPermissionAuthorizationHandler`
  checks scope as well, so this fails too. **Assert it even if no instance exists**, and say so if
  none does: a direction asserted with no current instance is the one that catches the future mistake.

**Reuse rather than re-enumerate.** If the T-072 enumeration can yield `(endpoint, plane, permission
name)` once and both guards read it, do that. **Two enumerations that could drift is the shape this
pair of tasks exists to remove.**

## Plant both directions

**Per `DEC-L-059a`, and the same reasoning that made your T-072 plant the right one.** A plant that
fails for the wrong reason proves the wrong guard:

- The plant must be a permission the catalog **does** define — otherwise you are re-demonstrating
  T-072's join, not this one.
- **Report the hash across before-plant / after-revert / at-HEAD**, as you did.

**If either direction cannot be made red, that direction is not asserted** — and you found a check
that could not fail two weeks of findings ago, so you know what one looks like from the inside.

  instance, **report it; do not fix it.** A scope or a plane is an authorization decision and it is
  the architect's, possibly the owner's. **Finding one is the result.**
- **Do not narrow `AuthorizationNameValidator`.** Settled — see below.
- **Do not touch `LocalizationEndpointRouteBuilderExtensions.cs:39-48`.** You found it hand-spells
  `$"Permission:{...}"` instead of calling `CreatePolicyName`, and that it happens to be correct.
  **Leave it.** Your own argument is why: the join covers the consequence however the string was
  built, so the hand-spelling is a tidiness question and this task is not a tidying task. **Recorded
  as a finding, deliberately not actioned.**

## The grammar divergence is settled — NO. Your correction is taken, and it improves the reason

**You walked reason two back before I checked it, and the walk-back is right.** Recorded in the form
that survives, because a rule resting on a mechanism that turns out to be wrong is a rule that fails
the next time someone leans on it.

**What I verified independently and stands:** `RoleAuthorizationDefaults.cs:36` delegates to the
shared validator; `RoleName.Create` is *non-blank, at most 100 characters* — no segment rule, no
character rule, tenant-authored. And the laxity is depended on more widely than your result said:
**five** construction sites use the two-segment `"test.permission"`, across
`PermissionAuthorizationTests.cs` and `PlatformPermissionAuthorizationTests.cs`, not one. **Those five
would go red on a narrowing** — so narrowing is not free even today, though the cost is test-side.

**What you corrected, and I confirm: no route maps a role policy.** The only `RoleRequirement`
construction in `src/` is `PermissionAuthorizationPolicyProvider.cs:68`, the provider building one on
demand. **The role-policy path is machinery with no caller**, which your own residual-bucket assertion
says from the other side.

**So the honest reason is:** narrowing would deepen an existing and unnoticed mismatch on a type that
deliberately has no grammar — **not** that it would break working behaviour. **Conclusion unchanged;
reason one is unaffected and is the one visible in your red line.**

**I would have approved "narrow the endpoint validator" as an obvious tightening.** The only thing
between that and a merged change was you reading the second file — and then, when the mechanism you
gave did not hold up, saying so unprompted rather than letting my verification find it.

### The finding that fell out of it — REPORT ONLY, NOT WORK

`RoleName` permits `Payroll Manager`. `IsValidRoleName` **rejects it** — a space is not an identifier
character. **The two are already inconsistent for ordinary tenant role names, before anyone narrows
anything**, and `CreatePolicyName` **throws** rather than returning false:

```
RoleAuthorizationDefaults.cs:11   throw new ArgumentException("Role names must use dot-separated identifier segments.")
```

**The error message asserts a grammar `RoleName` has never had.** So this is not drift between two
things that agreed once; it was written inconsistent.

**Nothing exercises it, because nothing maps a role policy** — which is precisely why it has gone
unnoticed and why it would arrive as an exception at route mapping, not a refusal, the first time
someone does. **Do not fix it in this task and do not open a guard for machinery with no caller.** It
is recorded so that whoever maps the first role policy finds it written down instead of discovering it.
