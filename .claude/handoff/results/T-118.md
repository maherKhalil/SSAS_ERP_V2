# THE FIX

```
Payroll.OneOffPaymentElementNotPayable   500  ->  422 (payroll.nothing_to_calculate)
```

**Unmapped from T-110 to T-118.** A one-off instruction naming an inactive element, or the derived net-pay
element, produced a **500 for a business refusal** — no exception anybody reads, no log entry, and a handler
that reads correctly.

## 422 rather than 409, and the two calculator refusals differ for a reason

**`DailySalaryHasNoWorkingDays` is 409 because waiting helps.** Close the attendance period, or give the
company a working calendar, and the identical request succeeds.

**This one never succeeds by waiting.** Somebody must change the instruction or the element. **A semantic
refusal of a well-formed request**, which is `NothingToCalculate`'s shape.

# THE COVERAGE, AND WHY IT IS NOT THE REGISTER'S

**`ModuleErrorMappingArchitectureTests` cannot see any error `PayrollCalculator` returns** — its closure
walks constructor parameters and the calculator is `static` (T-117). **So a fix it cannot observe needs
coverage that does not depend on it.**

`PayrollCalculatorErrorWireContractTests` asserts all four of the calculator's errors directly:

```
Payroll.NoIncludedEmployees             422
Payroll.PeriodBoundsInvalid             400
Payroll.DailySalaryHasNoWorkingDays     409

```

**And separately that none of them is a 500**, which is the claim worth making on its own — the exact code
is a judgement, the non-500 is the defect class.

**The file says when it should be reconsidered:** once T-119 widens the closure, three of the four become
redundant — **but it must not be deleted before the widened walk is SHOWN to reach them**, which is the
mistake it exists to prevent.
