### And the pid-reuse case, which is the one a naive check gets wrong

A **live** pid with a start time that does not match the label — what a reused pid actually looks like:

```
---   gate pid : 18196   started : 2000-01-01 00:00:00
--- RECLAIMING: pid 18196 is alive but started 2026-08-27 12:28:11, not 2000-01-01 00:00:00.
```

**Pid alone would have read this as a live gate and refused forever.** The failure direction if the
pairing is wrong is *refusing when we could have proceeded* — the safe side, and it is not traded away.

## Two defects the first run found, and neither was visible by reading

**I wrote this guard, read it, and shipped both.** They were found by starting two gates.

**1. The holder was created inside a `$( )` subshell.** `case "$(gate_lock_acquire)"` meant
`GATE_HOLDER_PID` never reached the parent, so the EXIT trap had nothing to kill — **the guard's first
act was to strand the instance it exists to protect.** Every abort leaked a holder that blocked the
next run.

This is the hazard **note 3 of this same file already records** for `reap_to_zero`: *"wrapping that
call in a pipeline or `$( )` would silently break all four."* Written down, and walked into anyway, in
the file that records it. The function now sets a global, echoes nothing, and says so where someone
would be tempted.

**2. Acquisition was detected by polling the holder's stdout.** `sqlcmd`'s stdout is **block-buffered**
when redirected to a file, so a `PRINT` before a 24-hour `WAITFOR` never reaches the file while the
holder lives. **The gate timed out reporting UNKNOWN on a lock it had successfully taken**, and refused
to run because of it. Detection now reads the label table, written by the same batch and visible at
once.

**Both failed in the safe direction and that is luck, not design.** One refused to start; the other
leaked a holder that made the *next* gate refuse. Had either failed permissively, the guard would have
been a green light with a lock-shaped comment on it.

### And a race the fix surfaced

Writing the label *after* acquiring leaves a window where the lock is held and the label still names
the **previous** holder — a challenger arriving there probes a dead pid and **reclaims a lock a live
gate has just legitimately taken.** The label is now written inside the acquiring batch, and
`gate_lock_steal` deletes the stale row in the same statement as the `KILL`, so a third gate arriving
mid-reclaim reads nothing, calls it undeterminable, and refuses.

## What is NOT covered, and should not be assumed

- **A second machine against the same instance** is guarded (the lock is instance-level) but its
  liveness probe would ask *this* box about a pid on *that* one. `host_name` is recorded by the DMV and
  is not currently consulted. **A cross-machine holder would be judged by a local pid lookup** — likely
  DEAD, and reclaimed wrongly. Everything on this box is one machine today; **the guard should learn
  `host_name` before that stops being true.**
- **`PHASE` was not re-run.** The guard is scope-independent and sits above the configuration loop, and
  `TASK` exercises every line of it. 69 minutes would confirm nothing this does not.
- **The EXIT trap** covers normal exit and this script's own aborts. It does **not** cover an external
  kill, which is why the reclaim path exists and why nothing depends on the trap.
