# T-043 — Pin `dotnet-ef` to the runtime's major version

- **Branch:** `agent/T-043-pin-ef-tools` — branch from `main`
- **Module:** Tooling
- **Issued:** 2026-08-26
- **Depends on:** T-037 merge (PR #89)

## Goal

You found this in T-041 and I verified the cause: **`global.json` pins the SDK to 8.0.423, and there is
no `.config/dotnet-tools.json`** — so `dotnet ef` resolves to whatever is installed globally, which is
**10.0.2**, against an EF Core 8 model.

The consequence is not cosmetic. Scaffolding a **data-only** migration produced one that drops and
re-adds three foreign keys on `SubscriptionPlan`'s owned collections — `Up` restoring them as
`Restrict`, **`Down` setting them to `Cascade`**. The tell was that the model snapshot came back
byte-identical.

**The next migration scaffolded here emits the same diff, and a reviewer looking at the migration alone
sees plausible foreign-key work and approves it.**

## Acceptance criteria

- [ ] **A local tool manifest pins `dotnet-ef` to the runtime's major version.** The tool is then
      resolved by the repository rather than by whatever a machine happens to have installed.
- [ ] **`dotnet tool restore` works from a clean checkout** — verify it, do not assume it. A manifest
      that requires a step nobody documents is the same defect one layer out.
- [ ] **Demonstrated, not asserted (`DEC-L-016` in spirit):** scaffold a throwaway no-op migration with
      the pinned tool and show it produces **no phantom foreign-key diff** — then delete it. If you
      cannot demonstrate it without leaving an artefact, say so rather than skipping it.
- [ ] **The manifest says why**, briefly — that the SDK is pinned in `global.json` and the tool must
      track it, with the phantom-diff symptom named so the next person recognises it if the pin ever
      slips.
- [ ] `git diff --stat` shows **at most two files**: the manifest, and a `.gitignore` entry only if one
      is genuinely needed.

## Files in scope

- `.config/dotnet-tools.json` — new
- `.gitignore` — only if required

## Out of scope

- **The three foreign keys.** They are correct as `AddSubscriptionCommercialPlane` created them, and
  the phantom migration was never committed. Touching them now would be the schema change this task
  exists to prevent.
- Any existing migration, including the T-041 seed.
- Upgrading EF Core, the SDK, or anything else to make the versions match from the other direction —
  **that is a different decision and not one I have made.**
- Any file under `src/` or `tests/`.

## Design constraints

- **Pin to the runtime, not to the newest 8.x that happens to be current.** The rule is that the tool
  tracks the model's major version; a floating patch inside 8 is fine, a floating major is the defect.
- **Do not commit a scaffolded migration**, even an empty one, to prove the point. Show the output and
  delete it.
- **`DEC-L-043` applies:** if the pinned tool produces a diff you did not expect — phantom or real —
  establish which is wrong before recording either.

## Tests required
