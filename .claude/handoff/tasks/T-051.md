# T-051 — Scaffold the Assets and Sales project skeletons, both at once

**Serialized. One window. No parallelism.** This task exists so that T-052 and T-053 can run
concurrently without sharing a single file. It is deliberately logic-free.

## Why this is its own task

Attendance's own introducing commit (`156dad4`) touched **19 files outside its module folder**.
Most are mechanical, but three are *counted* or *generated* and cannot be written twice
concurrently without one writer being wrong:

| Shared file | Why concurrent writes break |
|---|---|
| `tests/Architecture.Tests/ModuleEnablementArchitectureTests.cs` | Holds a **named assembly array** and `Assert.Equal(4, keys.Count)`. Two agents each adding a module both write `5`. The result is 6 modules asserting 5 — it fails loudly, but only after both merge. |
| `src/Platform/SSAS.Platform.Domain/Subscriptions/TrialSubscription.cs` | `The_trials_module_list_is_exactly_the_set_the_product_declares` asserts an **exact set**. Same failure mode. |
| `.../TenantErp/Migrations/TenantDbContextModelSnapshot.cs` | 2798 generated lines that must equal the sum of applied migrations. A textual merge produces a file that **compiles and is wrong**. |
| `SSAS.ERP.sln` | Appends to two sections. Mechanically resolvable, but resolvable-by-hand is not the same as safe-to-race. |

None of those are touched by writing domain logic. **They are all touched by wiring a module up.**
So the wiring happens once, before and after, and never during.

## Scope — create empty, compiling project skeletons only

For **each** of `Assets` and `Sales`, mirroring `src/Modules/Attendance/`:

```
src/Modules/Assets/SSAS.Assets.Domain/
src/Modules/Assets/SSAS.Assets.Application/
src/Modules/Assets/SSAS.Assets.Contracts/
tests/Assets.Tests/
```
…and the same five for `Sales`. **Do not create `.API` or `.Infrastructure` yet** — those are what
pull in the enablement descriptor and the model contributor, which are T-054's business.

Each project: `net8.0`, `ImplicitUsings`, `Nullable`, matching `Directory.Build.props` conventions.
`.Application` references `.Domain` and `.Contracts`. `.Contracts` references **nothing** — follow
the reasoning already written in `SSAS.GL.Contracts.csproj`, which states why a contracts assembly
holding project references re-creates the coupling `ADR-012` forbids.

Add all ten projects to `SSAS.ERP.sln` in **one** commit.

## Done when

- `dotnet build` is clean, **zero warnings**, with ten new empty projects in the solution.
- `tests/Assets.Tests` and `tests/Sales.Tests` each run and report zero tests, not zero projects.
- `ModuleEnablementArchitectureTests` is **untouched** and still asserts `4`. That is correct:
  no module has been declared yet, only projects created.
- Nothing under `src/Platform/`, no migration, no snapshot change.

## Explicitly out of scope

No entities. No `IModelContributor`. No `*ModuleEnablement` descriptor. No `Program.cs` change.
No migration. No trial-list change. If you find yourself editing a file that names the other
modules, stop — it belongs to T-054.
