# THE THINGS WORTH A PERSON'S ATTENTION

## 1. The container found a real constraint, and it was not a test problem

`IEmploymentStandingDirectory` began as a **required** constructor parameter on `UserEmployeeResolver`.
**Fourteen API tests failed DI validation:**

```
Unable to resolve service for type 'IEmploymentStandingDirectory'
  while attempting to activate 'UserEmployeeResolver'
  ... PlatformSupportAuthorityEndToEndHost, PlatformSupportAuthenticationEndToEndHost
```

**Those two hosts mount Platform with NO module registered.** Platform is beneath the modules and has to
stand up without them — a required dependency on a module-implemented contract inverts that.

**The fix is not a stub in two test hosts.** That is the "someone must remember" failure this whole task is
about, moved into the harness. The dependency is optional, and **absent is not an excuse to resolve — it is
a reason not to:** a host with no HR module has no employees, so nobody has a standing and nobody resolves.

**`A_resolver_with_no_standing_directory_refuses` asserts it**, because an optional dependency is a
fail-open waiting to happen unless the absent case is a test rather than a comment.

## 2. Why the refusal is at the seam and not in the reads — the argument, restated in the code

A check in each self-service read is the per-handler shape `REQ-SS-0003` rejected for permissions.
**Two scope resolvers exist today; leave balances would make three; the third would have to remember.**
The resolver is the one method all of them go through, so a self-service surface built next year inherits
the property without its author knowing it exists.

## 3. Why not on the identity — and this is measured, not preferred

`REQ-SS-0007` says *cannot authenticate*, which points at deactivating the tenant user. **It cannot close
this**, and the reason is in `CurrentUser.cs:31`: **permissions travel in the access token's CLAIMS, not a
live lookup.** Deactivation cannot revoke a token already issued — bounded at fifteen minutes by
`JwtOptionsValidator`, but not zero.

**The resolver runs per request against live state, so it closes that window at once.** With it in place, a
failure of T-091's cross-database deactivation degrades to incomplete cleanup rather than exposure.

**Named cost: this closes SELF-SERVICE, not AUTHENTICATION.** A terminated employee's tenant user can still
sign in and reach every administrative surface their grants allow. `REQ-SS-0007`'s literal words are T-091's.

## 4. The link is untouched, and it is asserted rather than promised

`REQ-SS-0006` / `AC-SS-0011` / `TS-SS-0009`. **The naive fix satisfies `AC-SS-0012` while destroying the
attributability the link exists to protect.** `The_link_is_untouched_by_a_refusal` reads the row back from
the database through a second context after a refusal.

**What closes is the resolution, not the record.**

## 5. Terminated, unknown and never-linked all answer the same 404

`attendance.no_linked_employee` / `payroll.no_linked_employee`, as the dangling-link precedent already
established. The caller did nothing wrong, cannot act on the difference, and a distinct code would disclose
that a link exists.

**Cost named at the call site: a terminated employee cannot tell "your access ended" from "you were never
linked."** That is an operational message to deliver out of band, not a fact for an API to leak.

## 6. `Inactive` still resolves, deliberately

`EmployeeStatus` has three values. **Only `Terminated` refuses.** `Inactive` is unpaid leave or
suspension — the employment relationship persists and is fully reversible — and refusing self-service to
someone on unpaid leave would be a rule nobody asked for. The mapping is in HR, so a fourth status later is
a change to one switch and not to a Platform file.

## 7. Three comments corrected under `DEC-L-073`

The task changed behaviour that three comments described, and two of them asserted the opposite of the new
ruling:

- **`EmployeePlacementDirectoryService.cs`** said *filtering on active here would sever self-service at
  termination through the back door.* **That outcome is now the intended one**, reached elsewhere. The
  predicate still does not belong there, for a reason that survives: one place decides, and it is the
  resolver.
- **`UserEmployeeLink.cs`** said *the guard on a terminated employee is on the identity's ability to
  authenticate.* Now: two guards, this one and T-091's, **neither on the link.**
- **`ModuleTenantContractArchitectureTests`** gained the two new exported names with the reason the edge
  is travelled in a new direction.

## A CORRECTION THE NEXT READER OF `cd4e89a` NEEDS

**My commit message on the `D7-M2.bundle` untracking is a stale claim.** It says *"--cached only: the file
stays on disk, exactly as it was."*

**It does not.** `git rm --cached` leaves the file only in the tree that ran it; the commit records a
**deletion**, so any working tree checking out across that commit removes the file. We share one tree, and
the owner's file was deleted by the commit that promised to preserve it.

**The architect restored it from `b2289e8`'s blob, byte-identical** — 1,642,992 bytes,
`d5da4bc0e2e417241b6e6aabbb5e6ffdd779188f`, present and correctly ignored. Verified present on the tree at
`36a0f81`.

**`DEC-L-077`:** untracking alone is not preservation. The correct sequence is untrack, commit, then restore
the file from the blob — or copy it aside first.

**And the root cause was mine:** `git add -A`, three times in T-089. The narrower habit — `git add -u` plus
each new file by explicit path, and read `git status --short` before every commit, confirming every `A` line
is a file you created — was used for every commit in T-090.
