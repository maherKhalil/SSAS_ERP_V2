## The priority question, and the answer is negative

**No committed migration was scaffolded this way.**

All **13** tenant migrations carry **zero `DropTable` in their `Up`**, checked per migration with `Up`
separated from `Down` **by line range** rather than by grepping the file whole.

**That method is the reason the answer is trustworthy rather than reassuring:** every one of those
migrations contains `DropTable` in its `Down`, so a whole-file grep would have reported the opposite
result with equal confidence.

**This is a tooling hazard, not a data one.** Nothing in the repository carries operations nobody
intended.

## The mechanism — established, and my own suspicion named the wrong component

**`ComposedTenantModelSource` is not involved.** It is a *runtime* `IModelSource` and is absent from the
design-time path entirely. The suspicion I carried into this task was right about the shape — a partial
model — and wrong about the part.

**The cause is a constructor parameter that is not passed.**

```
TenantDbContext(options, currentUser, currentTenant, dateTimeProvider,
                …, IEnumerable<ITenantModelContributor>? modelContributors = null, …)

OnModelCreating:  foreach (var contributor in modelContributors ?? []) contributor.Configure(modelBuilder);
```

`TenantDbContextDesignTimeFactory.CreateDbContext` constructs the context with **four arguments** and
omits the contributors. The design-time model is therefore built **with no contributors at all**, and
contains none of the module entities.

**The four contributors, listed rather than counted** (`DEC-L-044`): `HrTenantModelContributor`,
`GlTenantModelContributor`, `PayrollTenantModelContributor`, `AttendanceTenantModelContributor`.

### The join between "not composed" and "emitted as DropTable"

`Up` emits **exactly 32 `DropTable` and nothing else.** Those 32 are exactly the module-owned surface:

| Contributor | Tables dropped |
|---|---|
| Attendance | 7 — calendars, holidays, leave balances/requests/types, periods, records |
| GL | 6 — accounts, fiscal years/periods, journal drafts/draft lines, entries/lines |
| Payroll | 6 — elements, element assignments, employee compensation, periods, runs, run lines |
| HR | 13 — employees, departments, positions, grades, assignments, import/export runs |

**The tables the contributors configure are precisely the tables that get dropped**, because from the
design-time model's point of view they do not exist. That is the evidence; the count matching is only
corroboration.

## A correction to the figure this task was raised on

**"157 operations" was `Up` and `Down` combined.** The destructive part is **32 `DropTable` in `Up`**;
the remaining 125 are `Down` restoring them — 32 `CreateTable` plus 93 `CreateIndex`.

**My first pass reported "32 `DropTable` AND 32 `CreateTable`"** and I was one step from recording *"it
drops and recreates the entire module surface"* — a different and more alarming claim than the truth. I
had counted operation shapes across the whole file without separating the two halves. **It was caught
because the symmetry looked wrong, not because I was being careful** — `DEC-L-043` firing on the trigger
it was rewritten to have.

## The half that is NOT established, and is not being softened into a cause

**"The factory is broken, so every scaffold since has been destructive" cannot be the account.**

| Fact | Established by |
|---|---|
| The factory has **never** supplied contributors | `git log -S modelContributors` over that file returns **nothing, ever** |
| The factory **predates every module migration** | factory `ead6a27`, 2026-08-14; first module migration 2026-08-19; last 2026-08-25 |
| Before the contributor mechanism existed, `OnModelCreating` applied **only** the Platform-assembly tenant configuration namespace | `git show ea335c1^` — no module entities by any route |

**So the design-time model appears never to have contained module entities, while thirteen module
migrations were nevertheless scaffolded correctly.** Something else supplied a complete model on those
dates and I have not established what.

**Three candidates, none tested against the symptom:**

1. a **startup project** whose service provider EF preferred over the design-time factory;
2. a **different context or command** than the one I probed;
3. **hand-authored** migrations.

**This is recorded as unresolved rather than as a probable cause**, and that is the deliberate outcome.
Today produced four demonstrations that a plausible cause recorded confidently costs more than an open
question — two of them mine, one of which reached a task spec carrying the word *verified*.

### Why this half decides what the fix is

**If something else supplied a complete model for those thirteen, the factory is not the thing that
changed** — something else stopped working, was never used, or is used only under conditions nobody has
written down. **A fix to the factory would then look correct and be beside the point.**

## The fix, proposed and not applied

**Not proposed yet, and deliberately.** `DEC-L-045` applies to the proposal itself: a repair that makes
the scaffold quiet without making the model right would replace a loud defect with a silent one — which
is exactly what T-047 caught. **Until the historical half is settled, any fix I proposed would be a fix
to the half I understand, recommended for a defect I have only half explained.**

What can be said now: **the obvious repair — pass the contributors in the design-time factory — is
untested against the question of why it was ever unnecessary.**
