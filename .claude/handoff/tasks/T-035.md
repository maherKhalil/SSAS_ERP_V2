# T-035 — The commercial-plane schema: plans, subscriptions, entitlement grants

- **Branch:** `agent/T-035-subscription-schema` — branch from `main`
- **Module:** Platform (commercial plane)
- **Issued:** 2026-08-26
- **Depends on:** T-032 merge (PR #79). **Gated.**

## Goal

T-032 installed the seam. This gives it something to read.

FP-014's model documents specify the shape in full and every decision behind it is ruled, so this is
implementation against a settled design rather than a design task.

**The resolver is NOT switched in this task.** The transitional one keeps granting everything.
Switching it is the *cutover*, and it needs a decision I have not asked the owner for yet: with no
backfill and no default plan, a tenant without a subscription row reaches **no gated module** — which
is correct per `CON-0001` and is also how you lock out an entire existing estate in one deploy.
Building the store and flipping the source are two acts and this is the first.

## Acceptance criteria

- [ ] **Plan, plan-module grant, tenant subscription and entitlement grant exist in the Platform
      database**, on FP-014's `data-model.md`: **no cross-database foreign key in either direction**
      (`DEC-SUB-0009`), money as `ADR-027` `decimal(19,4)` inherited not restated, and **no commercial
      table in the Shared→Dedicated cutover inventory** (`DEC-SUB-0011`) — assert that last one, since
      an entity added to the Platform context could be swept in by a future reflection-based manifest.
- [ ] **The subscription is an append-only history with exactly one in force**, derived by ordering
      with **no closing column** (`OD-SUB-0008`), and **the append is strictly monotonic** — an append
      behind the present would rewrite what was in force when a metered overage was judged.
      **`PlatformDbContext` now has `PreventAppendOnlyMutation` (T-014), so `IAppendOnlyEntity` here is
      real enforcement rather than decoration** — that guard was built for this.
- [ ] **A migration that adds no backfill and no default plan**, and which **verifies per tenant
      database that it is not silently creating one** — the `DEC-POS-0026` shape, fail loudly rather
      than assume. It must be reviewable as a release-sequencing decision, so say in the migration
      what happens to a tenant with no subscription row once the resolver is switched.
- [ ] **The transitional resolver is untouched and still the only registered implementation.** The
      architecture test asserting that must still pass. If building the store makes that test awkward,
      **report it — do not relax it.**
- [ ] Gate green under `DEC-L-008`, **`Integration.Tests` runs** — this is persistence on the Platform
      context — and merged on green per `DEC-L-007`. Baseline: Architecture 470, Platform 986, API 692,
      HR 326, Finance 46, Payroll 56, Attendance 59, **Integration 782 both configurations**.

## Design constraints

- **A cap in force is a property of the subscription record live at that moment**, not of the tenant.
  Model it so a metered overage can be judged against the record in force when the usage occurred.
- **Entitlement resolves as plan ∪ additive grants, and a grant may never lower a cap** (`OD-SUB-0011`,
  `DEC-L-009`). The data model must make lowering **impossible or refused**, not merely undone.
- **Read `Tenant` and `Employee` first** and match the established aggregate conventions — value
  objects, `Result<T>` factories, audit columns, `RowVersion`. A novel shape is a defect even when it compiles.
- **`DEC-L-027` applies to this task's own documents**: if this makes an FP-014 statement false, say so.

## Tests required

- `Platform.Tests` — the aggregates and their invariants, especially monotonic append and the

- `Architecture.Tests` — no commercial table in the cutover inventory; the resolver still singular.
- `Integration.Tests` — the append-only guard **actually refusing** against real SQL. `Platform.Tests`
