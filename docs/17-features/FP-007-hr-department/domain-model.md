# FP-007 — Domain Model

## The aggregate

`Department` is an aggregate root in `SSAS.HR.Domain.Departments`, implementing
`AggregateRoot<Guid>`, `IAuditableEntity`, `ITenantOwnedEntity`, `ICompanyOwnedEntity`.

**It does not implement `IBranchOwnedEntity`, and that is a decision rather than an omission**
(`DEC-DEP-0001`). An architecture guard asserts the absence, because the next reader will otherwise assume it
was forgotten — Employee implements all three, and Department sitting beside it with two looks like an
oversight until something says it is not.

```
Department
  Id                     Guid, never generated by the store (ADR-013)
  TenantId               stamped by the persistence boundary
  CompanyId              stamped by the persistence boundary
  Code                   value object, normalized, unique within company
  Name                   value object, required, not unique
  ParentDepartmentId     Guid?, self-reference within the same company
  ManagerEmployeeId      Guid?, Employee in the same company
  Status                 Active | Inactive
  StatusChangedUtc/By    who moved it and when
  Created/Modified Utc/By  IAuditableEntity, stamped by infrastructure
  RowVersion             concurrency token
```

### What the aggregate does not let you do

There is no setter for `TenantId` or `CompanyId` beyond the ownership interfaces the persistence layer stamps
through. There is no way to set `Status` directly — only `Deactivate()` and `Reactivate()`, each of which
records who and when. There is no way to set `ParentDepartmentId` directly — only `ChangeParent()`, which
cannot be called without the ancestry evidence described below. This mirrors how FP-006 made `BranchId`
unreachable except through the sanctioned transfer channel.

## Value objects

`DepartmentCode` and `DepartmentName` follow the `EmployeeNumber` / `EmployeeFullName` pattern already
established in FP-006: construction validates, exposes `Value`, and `DepartmentCode` additionally exposes
`NormalizedValue` for the binary-collated uniqueness index.

## D2 — Hierarchy representation

**Decision `DEC-DEP-0005`: adjacency list — a nullable `ParentDepartmentId` on `Department`.**
Classification: **ENGINEERING-SETTLED.**

| | Adjacency list | Closure table | Materialized path |
|---|---|---|---|
| CRUD complexity | **Trivial** — one nullable column | A second table written on every insert and every move | A path string maintained on every move |
| Moving a subtree | **One row updated** | Delete and reinsert every ancestor pair for the whole subtree | Rewrite the path of every descendant |
| Ancestor query | Recursive CTE | **Single indexed join** | **Single `LIKE` prefix scan** |
| Descendant query | Recursive CTE | **Single indexed join** | **Single `LIKE` prefix scan** |
| Cycle prevention | Ancestor walk on re-parent | Detectable from the closure set | Detectable from the path |
| SQL Server support | Native recursive CTE, `MAXRECURSION` | Ordinary tables | Ordinary tables, or `hierarchyid` |
| Write complexity | **Lowest** | Highest — a denormalization that can silently drift | High, and path length caps depth |
| Future org-chart queries | Adequate at this scale | Best | Good |
| Maintainability | **Highest** — one column, no derived state to reconcile | A second source of truth for the same fact | A string that encodes structure |

**Why adjacency list wins here.** Closure tables and materialized paths both buy read performance by
maintaining derived state, and derived state that drifts from its source is a class of bug this codebase has
consistently refused to accept (see `TenantCutoverCopyPlan`, which derives the manifest rather than declaring
it). Department hierarchies are small — tens to low hundreds of nodes per company — and recursive CTEs are
comfortably fast at that size. Buying read performance with a reconciliation risk is the wrong trade at this
scale.

The migration path is open: a closure table can be added later as a pure read optimization, derived from the
adjacency list, without changing the aggregate. The reverse is not true.

## D3 — The acyclicity invariant

**Decision `DEC-DEP-0006`.** Classification: **ENGINEERING-SETTLED.**
`BRULE-DEP-0009` is not "validate no cycles". It is the following, exactly.

### Create

A Department is created with `ParentDepartmentId` either null or referencing an existing Department in the
same company. **A newly created Department cannot participate in a cycle** — it has no descendants yet — so
create requires only the same-company check (`BRULE-DEP-0008`). No ancestry walk is needed, and none is
performed.

### Change parent

`ChangeParent(newParentId)` refuses in this order:

1. **Self-parent.** `newParentId == Id` → refuse `DepartmentErrors.ParentIsSelf`. Checked in the aggregate,
   with no I/O.
2. **Cross-company.** The new parent must resolve in the same tenant and company → refuse
   `DepartmentErrors.ParentInDifferentCompany`.
3. **Inactive parent.** A Department may not be moved beneath an `Inactive` parent → refuse
   `DepartmentErrors.ParentInactive`.
4. **Descendant-as-parent.** The new parent must not be a descendant of the Department being moved → refuse
   `DepartmentErrors.ParentIsDescendant`.

Check 4 is the one that requires evidence the aggregate cannot obtain itself. It is answered by walking
**upward from the proposed new parent** to the root: if the Department being moved is encountered, the move
would close a cycle. Walking up from the candidate is O(depth); walking down over descendants is O(subtree)
and would be the wrong direction.

### Where the ancestry evidence comes from

The application handler resolves the ancestor chain and passes it to the aggregate as a value the aggregate
cannot fabricate — the same shape FP-006 used for authorization evidence, where `EmployeeReadScope` is
unconstructable outside its resolver. `ChangeParent` takes a `DepartmentAncestry` that only the repository can
produce, so **a handler that forgot to check cannot call the method at all**. A rule enforced by remembering
to call a validator is a rule that will eventually not be called.

### Transaction boundary and concurrency

The ancestor walk and the update execute in **one transaction**, and the moving Department's `RowVersion` is
the concurrency token. That alone is not sufficient: two concurrent moves of *different* departments can each
read a consistent ancestry and together produce a cycle — move A under B while simultaneously moving B under
A. Each sees a legal state; the pair is illegal.

**Serialization mechanism (`DEC-DEP-0006`).** Re-parent operations within one company serialize on the
company. The handler takes the same per-scope application lock pattern the platform already uses for tenant
cutover ownership, keyed on `(TenantId, CompanyId)`, for the duration of the ancestry read and the update.
Departments are re-parented rarely — this is an organizational change, not a transaction — so the contention
cost is irrelevant and the correctness gain is total.

The alternative considered and rejected was raising the isolation level to `SERIALIZABLE` for the ancestry
read. It would work, and it would make an unrelated, invisible property of the transaction responsible for a
named business invariant. The explicit lock says what it is protecting.

### Database-level defence

An adjacency list cannot express acyclicity as a SQL Server constraint. The self-parent case **can** be
expressed and is: `CK_Departments_ParentIsNotSelf` (`[ParentDepartmentId] <> [DepartmentId]`). The general
case is enforced in the application, transactionally, and proven by `TS-DEP-0028` through `TS-DEP-0031`
against real SQL — not by unit tests over a fake.

This asymmetry is stated plainly rather than papered over: **one branch of `BR-HR-0008` has a database
guarantee and the rest has a transactional one.** A trigger-based full check was rejected because the tenant
schema's trigger inventory is itself asserted by an architecture guard, and adding business logic to a trigger
would hide it from every reader of the domain.

## Employee changes

`Employee` gains:

```
  DepartmentId           Guid, required for employees created after FP-007 (OD-DEP-001)
```

and one operation, `ChangeDepartment(newDepartmentId, evidence, actor, occurredUtc)`.

`DepartmentId` gets **no public setter**, exactly as `BranchId` has none. The reasoning is identical: a
mutable ownership-adjacent field is a field that will eventually be mutated by an ordinary update. See
`DEC-DEP-0015` and §14 of [`decisions-approved.md`](decisions-approved.md).

## Domain events

`DepartmentCreated`, `DepartmentParentChanged`, `DepartmentManagerAssigned`, `DepartmentManagerCleared`,
`DepartmentDeactivated`, `DepartmentReactivated`, `EmployeeDepartmentChanged`.

These follow `ADR-009` and the existing `SSAS.HR.Domain.Events` pattern. They are raised; no handler is
introduced by this package. `EmployeeDepartmentChanged` is the natural seam through which a future
`EmployeeDepartmentAssignment` history would be written if `OD-DEP-004` chooses to introduce it — which is
why it is raised now even though nothing consumes it.
