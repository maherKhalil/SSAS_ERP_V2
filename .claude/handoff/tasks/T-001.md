# T-001 — Correct the "Current Implementation State" section of START-HERE.md

- **Branch:** `agent/T-001-start-here-state`
- **Module:** Docs / cross-cutting
- **Issued:** 2026-08-25
- **Depends on:** none

## Goal

`docs/START-HERE.md` is the repository's mandatory entry point, and under its own precedence
rule ("Documentation wins") it is authoritative. Its **Current Implementation State** section
(lines 257–274) is factually wrong: it says *"FP-008 HR Position is approved for implementation
and not yet built"* when FP-008 shipped and five further packages shipped after it. Every agent
and developer onboarding through that section is being told to build things that already exist.

This task makes that one section true. Nothing else.

## Acceptance criteria

- [ ] The section no longer describes FP-008 as unbuilt; `Position`, `JobGrade` and `SalaryGrade`
      are recorded as delivered, and `ADR-027` is recorded as activated rather than "drafted alongside".
- [ ] FP-009 (import/export) and FP-011 (GL foundation), FP-012 (Payroll), FP-013 (Attendance)
      are each recorded as delivered, each with a traceable anchor — the PR number or merge commit
      sha that landed it on `main`.
- [ ] FP-010 (Employee Documents) is recorded as **CLOSED — deferred to V5 Document Management
      (`OD-DOC-009`)**, so a reader does not treat it as pending HR work.
- [ ] Every factual claim added to the section is traceable to a merge commit, a file path, or a
      feature-package `status:` line that exists in this repository today. No claim you cannot cite.
- [ ] `git diff main...agent/T-001-start-here-state --stat` shows **exactly one file changed**:
      `docs/START-HERE.md`.

## Files in scope

  (line 257 to the line before `# Repository Success Criteria`).

Everything else in that file, and every other file in the repository, is out of scope.

## Design constraints

- Match the voice and structure of the section as it stands: prose paragraphs with **bold** lead-ins,
  not a table and not a bullet list. It is written to be read top to bottom by someone new.
- Keep the closing paragraph's warning intact in substance — that the repository state and the
  approved Feature Packages are authoritative, and that a reader must not resume completed work on
  the strength of a stale heading. That warning is the reason this section is trustworthy at all;
  it is what makes the section self-correcting.
- Do not invent milestone names, dates, or sprint numbers. Where you cannot cite something, say
  less rather than more.
