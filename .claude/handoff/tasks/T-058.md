# PART A — the gate does not enforce the zero-warning bar it is credited with

*(This was `T-057`. Its full text stands; the essentials are here.)*

`DEC-L-008` condition 1 says *"the build succeeds at zero warnings; a warning you introduced is a
failure."* Nothing enforces it:

```
scripts/gate.sh:457       greps "Warning(s)|Error(s)|..." and PRINTS
GATE_FAILED=1             set only from suite failures
Directory.Build.props:8   <TreatWarningsAsErrors>false</TreatWarningsAsErrors>   ← explicit
```

Of the four merge conditions, 2 and 3 are suite runs and 4 is the count comparison. **Condition 1 is
held entirely by the coder choosing to honour it, under `DEC-L-007`, which merges on green without
architect review.** It has never been violated, which is what makes it read as a property of the
instrument rather than of a person.

**Establish the cost first.** Report how many warnings exist today, per configuration. Note 9 records
the first Release run exposing `CA1826` that Debug did not.

**Two candidate mechanisms, and your own objection to the second is on record:** a grep-based check
catches warnings in the build the gate performs and **nothing about a build it does not** — and
`--no-build` is on every suite invocation, so building in an IDE and running the gate over that
output would report clean over a build the gate never saw. **Establish that before choosing.** There
may be a third. Bring measured counts and a recommendation, not a menu.

# PART B — the gate cannot tell whether it is the merged gate

**This failed three times today, in one tree, by two windows.** The third was this afternoon: the
shared tree sat at `fbd9726` while `ClaudeBranch` was `82baf53`.

The coder's own statement of it, which is the size to build against: **the tree is stale by default,
and the merge that makes it stale is the one that just succeeded.**

And it is live on another tree right now, not hypothetical:

```
SSAS_ERP_V2-chain-test   scripts/gate.sh = 81e342e   2026-08-25
                         grep -c GATE_SCOPE -> 0
```

That tree would run the **pre-`GATE_SCOPE`** gate and report exactly what it has always reported.
Nothing about the run would look wrong. **It carries both hazards at once** — it can reap a live
run's catalogs *and* it predates the scope split.

**Two properties you named and must not let collapse into one:**

- The probe is only as fresh as the last fetch.
- **A gate that refuses when it cannot reach the remote stops all work offline.** Fail-closed is
  right where the failure is destructive — that was `T-056`'s trade, where proceeding wrongly
  destroys a 69-minute run. **Staleness is a different trade and must not inherit the concurrency
  answer.** Offline is a normal condition; a colliding gate is not.

Detection and policy stay separate here as they did in `T-056`. **Bring the detection; state the
policy options; do not weld them.** If the honest answer is *warn loudly and proceed*, say so and
argue it — that is a legitimate outcome and a different one from `T-056`'s refusal.
