# ⚠ FIRST, BECAUSE YOU ASKED FOR BUCKET 1 FIRST — AND THE BIGGEST FINDING IS NOT IN ANY BUCKET

**`SetLeaveEntitlementCommandHandler` is a read-then-write with NO database backstop.**

```
handler   balances.GetForEmployeeAsync(company, employee, leaveType, year)
          if (existing is not null)  -> SetEntitlement          (upsert)
          else                       -> add a new balance
schema    LeaveBalance has NO unique index. None. Only two foreign keys.
```

**Two concurrent requests both read null and both insert.** The employee ends with two balance rows for one
leave type and year, and `GetForEmployeeAsync` returns an arbitrary one thereafter.

**This is the third instance of the same shape this fortnight** — leave-request overlap (T-146/T-148, closed
with a filtered unique index plus an application lock) and the journal number (T-165, closed at commit by
`UX_GlJournalEntries_Tenant_Company_Year_Number`). **This one is closed by nothing.**

**`Attendance.LeaveBalanceConflict` is declared and mapped for exactly this condition and returned by
nothing** — which is how the sweep surfaced it. **I am not fixing it in an establish**; it needs a unique
index, a migration, and a decision about the concurrent-insert answer. **Recommend it becomes its own task.**

### ⚠ The declaration form you predicted was not the one that was missing

You warned that a multi-line `new(` would hide declarations from a shape-matching grep. **It did not — my
regex spans newlines.** What it missed was a second form entirely:

```csharp
public static Error Inactive(string accountCode) => new(
  "Gl.AccountInactive", $"Account '{accountCode}' is inactive...");
```

**Eight codes are declared by parameterised FACTORY, not by field**, including `Payroll.RunNotPostable`,
`Payroll.PayElementUnmapped` and `Gl.AccountInactive`. **A sweep that knows only the field form reports
them as codes that exist nowhere** — and the floor check caught it, not the sweep.

### ⚠ And the returned set had a false-positive class of MY making, at 4x the signal

**The first pass reported THIRTY unreferenced members. The true figure is eight.** Twenty-two were errors
declared *and used inside their own file* — `AttendanceReadScope`, `GlScopeResolver`, `PayrollReadScope`
each declare and return their own scope errors. **My usage search excluded the declaring file**, so a class
that is its own only consumer looked entirely dead.

**Had I reported the thirty, five of the seven "modules" in that list would have been fiction, and the
recommendation would have been to delete live authorization errors.**

**Your layer concern was already covered**, and I should say so plainly rather than take credit for it: the
walk searches **every `.cs` file under `src/`** for a qualified reference, so a code returned by a domain
aggregate is seen. Control: `JournalErrors.AlreadyReversed` is returned only by the aggregate's own guard
and is correctly **absent** from the unused list.

### Bucket 2 — `Attendance.RecordDateOutsidePeriod`

`RecordAttendanceCommandHandler` answers `AttendancePeriodErrors.NoOpenPeriod` and
`AttendancePeriodErrors.PeriodClosed` instead. **The condition is covered and named better than this code
names it** — "no open period" and "period closed" tell an operator what to do; "date outside period" does
not. Surplus.

### Bucket 3 — `Payroll.PayElementCodeImmutable`, and it is `Gl.JournalImmutable`'s exact twin

**`UpdatePayElementCommand` has no `Code` field**:

```csharp
public sealed record UpdatePayElementCommand(
  Guid PayElementId, string? Name, decimal DefaultRateOrAmount, int CalculationOrder, Guid? GlAccountId);
```

**The code cannot be changed because the command cannot carry it.** Same structural enforcement as T-166,
same recommendation: **keep, and assert the absence** so someone adding `Code` to that record meets a test
rather than a mapped-but-dead 409.

⚠ **And its sibling is NOT dead**: `AccountErrors.CodeIsImmutable` (`Gl.AccountCodeImmutable`) *is*
returned. **Two modules, the same rule, one enforced by a check and one by the command's shape** — worth
knowing before anyone "makes them consistent".

### The two I am not classifying

`AccountActionToken.InvalidHash` and `Tenant.Required` are **declared, unmapped, and unreferenced**. Both
sit in Platform's authentication surface where a wrong deletion is worst. **Per your asymmetry rule they
come to you**: a wrongly-kept code costs a line, a wrongly-deleted one costs a business rule with no trace.
