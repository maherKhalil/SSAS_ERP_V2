# T-055 — `GATE_SCOPE`: separate the per-task gate from the phase-exit gate

**Implements `DEC-L-051`.** Tooling task. This is the highest-value change available right now:
it buys back roughly an hour per persistence-touching task, and it is a scoping change to a script,
not a change to what is tested.

## The defect, stated precisely

`DEC-L-008` condition 3 has always scoped `Integration.Tests` to tasks that touch persistence, a
migration, an EF configuration or the cutover inventory. **The rule was already tiered.** But the
same condition says *"run it through `scripts/gate.sh`"* — and that script's own first line calls
it `THE PHASE-EXIT GATE. FULL SUITE, BOTH CONFIGURATIONS.`

So there has been no way to run Integration with its memory preconditions and catalog reaping
intact without also buying every other suite, twice. The script's header records the cost it was
measured at on this box under LEAN:

```
Integration Debug    32 m 21 s      Integration Release  32 m 35 s
```

**About 65 of the gate's ~75 minutes are those two legs**, and one of them tells a per-task change
almost nothing the other did not.

## The change

Add `GATE_SCOPE`, defaulting to `TASK`, alongside the existing `GATE_MODE`. Keep them orthogonal:
`GATE_MODE` is about *this box's resources* (LEAN/FULL); `GATE_SCOPE` is about *what question is
being asked* (per-task confidence vs phase-exit confidence). Do not fold one into the other.

| `GATE_SCOPE` | Suites | Configurations |
|---|---|---|
| `TASK` (default) | Architecture, Platform, HR, API, plus the changed module's suite. Integration **only** when asked for. | Debug only. |
| `PHASE` | All eight, exactly as today. | Debug **and** Release, exactly as today. |

Under `TASK`, Integration is opt-in — the coder knows whether condition 3 applies and the script
cannot. A flag or a second variable is fine; **do not try to infer it from the diff.** An inference
that is wrong in the permissive direction is a silent hole in `DEC-L-008`, which is the shape of
defect this repository has now recorded four times.

**`PHASE` must remain byte-for-byte the gate that exists today.** Its Debug/Release pairing is
argued in header note 7 and the reasoning stands: a Debug Integration run once failed 1 of 729 and
the failure was **unrecoverable**. This task narrows *when* that runs, never *what* it runs.

## What must not change

- All four preconditions, both floors, the sibling-`testhost` refusal and the `SSAS_%` reaping apply
  to **both** scopes. A per-task run that skipped the memory floor would fail at 14 MB free with no
  TRX, which is the 2026-08-24 failure the floor exists to prevent.
- The terminal `exit $GATE_FAILED` from T-016 stays, with 1 distinct from the 2–5 precondition
  codes. A narrower gate that reports success on a red run is worse than the wide one it replaced.
- `[GATE RED]` / `[GATE GREEN]` / `[GATE COMPLETE]` output must state **which scope ran**. A log
  that does not say what it covered will be read a week later as if it covered everything —
  `DEC-L-045`, prefer a loud divergence to a silent one.

## Done when

- `GATE_SCOPE=TASK scripts/gate.sh` completes green without an Integration leg, in minutes.
- The same with Integration requested runs it **once**, in Debug, preconditions intact.
- `GATE_SCOPE=PHASE scripts/gate.sh` is indistinguishable from today's run — same eight suites, both
  configurations, same counts against the recorded baseline.
- A red suite exits non-zero under **both** scopes. Verify it, do not assume it: this is the exact
  hole T-016 found, and it was found in a script that looked correct.
- Header note 7z is updated to document both variables and the measured `TASK` cost, so the next
  reader estimates from a measured figure rather than from the FULL shape — the mistake note 7z
  already records someone making.
