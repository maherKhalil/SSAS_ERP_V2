**Link 1 is the dangerous half and it is true: `TenantUser` does carry the interface.** The ADR says so

## The sharp version, which the ADR states correctly but does not spell out

**Residency is decided by MODEL MEMBERSHIP. Not by the interface, and not by the assembly.** Both of
the other candidate explanations are false, and I can name the counter-example for each:

- **Not the assembly.** `SSAS.Platform.Domain.Branches.Branch` and `SSAS.Platform.Domain.Companies.Company`
  are Platform-Domain types that appear in the **tenant** model snapshot and not in the Platform one.
  **Platform-Domain types do travel.** They are declared as `DbSet`s on `TenantDbContext.cs:84,86`.
- **Not the interface.** `TenantUser` carries `ITenantOwnedEntity` and stays.

`TenantDbContext.cs:117-119` names the mechanism in its own comment: `ApplyConfigurationsFromAssembly`
would pull every platform entity into the tenant model, so it deliberately applies from a restricted
source instead.

**The consequence for FP-015, and it is the thing I would put in `data-model.md`:** the mapping's
residency is **one line of model composition**. If the mapping entity is configured on the Platform
context it never travels, whatever interfaces it carries. **If anything ever contributed it to the
tenant model it would be swept into the copy silently** — and `TenantUser` already carrying the
interface shows the guard-rail is not the interface.

**And the existing residency guard cannot be reused for it.**
`SubscriptionResidencyArchitectureTests.cs:45-58` protects the commercial types by asserting they
**lack** `ITenantOwnedEntity`. That method is unavailable for anything that has it, which is the case
the mapping most resembles.

**Five of them hold a user identifier. Every property of all five, and every one is accounted for:**


**No sixth identifier exists anywhere in the five.** Every one is `TenantId`, `RoleId`, `BranchId` or
`CompanyId`, and each is the association the type is named for.

**The shape argument is stronger than the enumeration.** The pattern a mapping would take —
`(TenantUserId, <thing>Id)` on its own Platform-resident table — **already exists three times**:
branch, company, and role. **There is no fourth for employee.** The absence is not a gap in a family
of one; it is the missing member of a family of three.

**Corroborating, and it is only corroboration:** `Employee` appears **twice** in all of
`SSAS.Platform.Domain`, both in comments on `TenantSubscription.cs:11,30` citing
`EmployeePositionAssignment` as precedent for an unrelated property.

**The other side is also empty.** `Employee` (`Employee.cs:38-39`) carries `TenantId`, `CompanyId`,
`BranchId`, `DepartmentId`, `PositionId`, `EmployeeNumber`, `NationalId`, `FullName`, dates, status
and audit. **No user, identity or subject.**

## 3. No read service resolves one from the other, and none can

# 4–5. THE INPUTS

## 4. The tenant-user aggregate

```
type        SSAS.Platform.Domain.TenantUsers.TenantUser        TenantUser.cs:9
identifier  AggregateRoot<long>  ->  Id is long
table       "TenantUsers", PlatformPersistenceConstants.Schema  TenantUserConfiguration.cs:13
PK column   "TenantUserId", UseIdentityColumn()                 TenantUserConfiguration.cs:14-15
```

**`UseIdentityColumn()` means values are assigned by the Platform database on insert** — a `long`
IDENTITY, not a client-generated key.

**Note `IdentityId` is a different thing.** `TenantUser.IdentityId` (`long`) points at `Identity`, the
authentication record. **A tenant user is the tenant-scoped membership; an identity is the login.**
One identity can hold several tenant users. Which of the two the mapping names is a decision with
consequences and it is yours — I am reporting that they are two.

## 5. What identifies an `Employee` across the boundary

```
Employee : AggregateRoot<Guid>        Employee.cs:38-39     ->  Id is Guid
```

**So the mapping is asymmetric: a `long` on the user side, a `Guid` on the employee side.**

### The precedent you asked me to check rather than trust — and it does not say what the citation implies

`ADR-030` cites `ADR-017`'s `CreatedBy`/`ModifiedBy` as precedent for a plain scalar. **The precedent
is real and it is stronger than "a scalar" — but it keys on something else.**

```
IAuditableEntity          string? CreatedBy / ModifiedBy
written from              ApplicationExecutionContext.cs:17-22  ->  currentUser.UserId
and UserId is             CurrentUser.cs:9  ->  principal.FindFirstValue(JwtClaimTypes.Subject)
and a Subject is          AuthenticationSubject.cs — a string <= 256 chars; local ones are "local:{guid:N}"
```

**`CreatedBy` holds the identity SUBJECT, not the `TenantUserId`.** So the product does already store a
Platform-plane user reference as a plain scalar on tenant-database rows — `Employee.CreatedBy` is
exactly that, in production data. **But it is a subject string, not the `long` identity key**, and it
identifies the *login* rather than the *tenant membership*.

**A `TenantUserId` is available in a request** — `CurrentTenantUser.cs:17-18` exposes it as `long?` from
the session claim. **The audit fields simply do not use it.** So if the mapping keys on `TenantUserId`,
`ADR-017` is a precedent for the *technique* and not for the *key*.

### And the nearest precedents are two tables of exactly this shape

**`UserBranchAccess` and `UserCompanyAccess` are already what the mapping would be:**

```
UserBranchAccessConfiguration.cs:12-22    TenantUserId (long, required) + BranchId (Guid, required)
UserCompanyAccessConfiguration.cs:12-22   TenantUserId (long, required) + CompanyId (Guid, required)
```

**Platform-resident, `long` + `Guid`, and NO `HasOne`/`HasForeignKey` on either** — plain scalars with
covering indexes, because `Branch` and `Company` rows live in the tenant database. **That is
`ADR-030` Decision 4 already implemented twice.** The mapping is a third instance of an existing
pattern rather than a new one.

**One inconsistency in that pattern, which you will have to resolve for the third:**

```
UserBranchAccess    : Entity<long>, IAuditableEntity                        no ITenantOwnedEntity
UserCompanyAccess   : Entity<long>, IAuditableEntity                        no ITenantOwnedEntity
TenantUser          : AggregateRoot<long>, IAuditableEntity, ITenantOwnedEntity
```

**All three are Platform-resident and all three carry a `TenantId` property.** Two decline the
interface; one takes it. **There is no consistent convention**, so whichever the mapping does will look
like it follows a rule, and there is no rule. Given Decision 1 above, declining it is the
belt-and-braces choice — but that is a preference and it is yours.
