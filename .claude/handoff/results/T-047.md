# T-047 result — ownership foreign keys exempted from the `Restrict` loop

- **Status:** GATE RUNNING (to be stamped)
- **Branch:** `agent/T-047-ownership-delete-behaviour` — branched from `main` at `9c49204`
- **Commit:** `42c8f4c` — fix(T-047): exempt ownership foreign keys from the Restrict loop
- **Reported:** 2026-08-26

## What was wrong

`PersistenceDbContext.OnModelCreating` set `DeleteBehavior.Restrict` on **every** foreign key, ownership
keys included. The migrations snapshot format **serialises no delete behaviour for an owned
relationship** — ownership implies `Cascade` on rehydration — so the model disagreed with its own
snapshot **permanently and unfixably**, and the differ was right to report it.

**Every migration scaffolded in this repository carried six spurious foreign-key operations.** It cost
two wrong diagnoses (T-041's tool-skew claim, T-043's `global.json` cause) before anyone read the loop,
**which carried no comment at all** — in a file whose next block spends a paragraph on why auditing hooks
the innermost `SaveChanges` overloads.

## Where I disagreed with the spec, and where it did not change the answer

The spec argued `Restrict` on an ownership key is **semantically meaningless**. **It is not.**

Through EF it is inert: owned rows are deleted with their owner by definition, and EF ordered those
deletes itself. **Via raw SQL it is not** — `DELETE FROM SubscriptionPlans` against a plan nobody is on
**failed** under `Restrict` and **succeeds** under `Cascade`, taking the plan's module grants, limits and
prices. T-035 already ships a test establishing that raw SQL is outside the write boundary, so the route
is live rather than theoretical.

**Why it does not change the answer, in the order that matters:**

1. **It was never a protection anyone chose** — a side effect of a blanket loop with no comment is not a
   design decision being reversed.
2. A plan **any tenant is on** is still protected by `TenantSubscriptions`' reference key, which keeps
   `Restrict`. The exposure is a raw delete of a plan nobody is on.
3. `SubscriptionPlan`'s lifecycle **has no removal** — retired, never deleted, because historical
   records point at it.

**The precision mattered because the file now has to say what was given up.** "Meaningless" would have
licensed a claim that nothing was lost.

## The migration is hand-written, and that is the finding

**EF generated it empty.** Migrations diff **the snapshot against the model, never the database against
the model** — and the snapshot never recorded `Restrict`, because it cannot. So after the change
model = `Cascade` and snapshot = `Cascade`, and the scaffold is empty. **Criterion 1's demonstration
succeeds.**

**But the database still had `Restrict`**, and no future scaffold would ever notice. **Left there, the
change would have traded a loud divergence for a silent one** — six operations in every migration is a
self-announcing nuisance; a schema that quietly disagrees with the model, with nothing that will ever
report it, is worse.

So `Up` was written by hand, and the migration says EF generated it empty and this is the only
reconciliation that will ever be offered. `Down` restores `Restrict` exactly.

## Scope, measured rather than inferred

| | Finding |
|---|---|
| Owned declarations in production code | **five** |
| `OwnsOne` sharing the owner's table (no schema FK) | `SalaryGrade.Band`, `TenantSubscription.Term` |
| `OwnsMany` with a schema FK | the three on `SubscriptionPlan` |
| **Ownership FKs in the MODEL** | **four** — the three plus `SubscriptionTerm` |

**My earlier "three is the entire affected set" was right about the schema and wrong about the model.**
`TenantSubscription.Term` was carrying `Restrict` like the rest; it was invisible in migrations only
because table-sharing produces no foreign key.

**Reference foreign keys: 36, all still `Restrict`**, asserted so the exemption cannot be read as a
relaxation.

## The guard, and the instrument that silently did nothing

**Test 1** — ownership keys must be `Cascade`. **Test 2** — all 36 references must be `Restrict`.
**Test 3** — the four owned relationships asserted **by name**, not counted (`DEC-L-044`: a count says
the scan was not empty, the names say it is the right set).

**The demonstration is a recorded experiment and the file says that is weaker than an executing test.**

```
git stash push -- src/BuildingBlocks/.../PersistenceDbContext.cs
dotnet test --filter Ownership_foreign_keys_keep
  -> FAILS: Offenders: PlanLimit (Restrict), PlanModuleGrant (Restrict),
            PlanPrice (Restrict), SubscriptionTerm (Restrict)
git stash pop
```

**I built an in-process probe first and it did not reproduce.** A two-entity `PersistenceDbContext` with
one owned collection reported `Cascade` whether the pre-T-047 loop was applied or not — the mutation does
not survive model finalisation on that shape. **It would have asserted nothing while looking like a
demonstration**: `DEC-L-016`'s exact failure, one level up, inside the test written to satisfy
`DEC-L-016`.

**I could have tuned the fixture until it went red and nobody would have known.** The failed attempt is
recorded rather than deleted, so the next reader does not rebuild it.

**And the transferable part is not vigilance.** I caught it because the probe contradicted a real model
whose behaviour I had already measured. **Had I written the probe first and never run the stash
experiment, I would have shipped it green and believed it.** The mechanism is: *validate a probe against
a case whose answer you already know* — a fixture checked only against the outcome it was built to
produce cannot distinguish working from inert.

## What the Integration suite asserts

Not that the change is harmless — **what the database now does**:

1. **The concession.** A raw delete of an unreferenced plan cascades to its three owned rows. If someone
   later decides that cost is unacceptable, this is what tells them exactly what they are buying back.
2. **The surviving protection**, matched to
   `FK_TenantSubscriptions_SubscriptionPlans_SubscriptionPlanId` **by name** — so it is that key doing
   the work rather than an incidental failure.
3. **The schema read from `sys.foreign_keys`**: `CASCADE` on the three, `NO_ACTION` on the reference.
   **Load-bearing for a reason specific to this change** — the migration is hand-written, EF will never
   regenerate it, and nothing else in the build would notice if someone tidied away an empty-looking
   file.

## The finding that outranks this task — T-048

**Scaffolding a no-op migration against `TenantDbContext` produces 157 operations, opening with
`DropTable` on `AttendanceCalendarHolidays` and `AttendanceLeaveBalances`**, with EF's own
*"may result in the loss of data"* warning.

**Established as not mine before reporting**: stashed the `PersistenceDbContext` change, re-scaffolded,
**157 identical**. Pre-existing and unrelated. Both probes removed and `TenantDbContextModelSnapshot`
restored to `HEAD` exactly.

**Anyone scaffolding a tenant migration today and trusting the output would drop shipped module tables.**
Suspected cause — the design-time factory composing a partial model through `ComposedTenantModelSource` —
is recorded **as a suspicion**, untested against the symptom.

**And a limit on `DEC-L-045` that this case establishes:** *prefer a loud divergence to a silent one* was
right for the Platform context. Here **the loudness is the danger** — 157 operations plus a loss-of-data
warning reads as *"a big migration, review carefully"*, and someone reviewing carefully would still be
reviewing a migration that should not exist at all. Volume and a warning together make destructive output
look like legitimate work.
