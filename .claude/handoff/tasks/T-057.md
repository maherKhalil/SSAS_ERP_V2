# T-057 — `DEC-L-008` condition 1 is the only one nothing checks

**Queued behind T-055 and T-056.** Do not start while either is in flight — same file.

## The finding

`CODER.md` and `DEC-L-008` both say the build succeeds **at zero warnings**, and that *"a warning
you introduced is a failure."* Nothing enforces it.

```
scripts/gate.sh:457       greps "Warning(s)|Error(s)|Build succeeded|..." and PRINTS
GATE_FAILED=1             set at :515 only, inside the SUITE loop
Directory.Build.props:8   <TreatWarningsAsErrors>false</TreatWarningsAsErrors>
```

The third line is what makes this a hole rather than a gap: warnings-as-errors is not unset or
defaulted, it is **explicitly `false`**. So a warning-laden build succeeds, the gate prints the
warnings, `GATE_FAILED` stays `0`, and the gate reports green.

Of `DEC-L-008`'s four conditions, 2 and 3 are suite runs and 4 is the count comparison the architect
asks about. **Condition 1 is held entirely by the coder choosing to honour it** — under `DEC-L-007`,
which merges on green without waiting for the architect.

**It has never been violated, and that is what makes it dangerous.** Every run has been clean, so
the sentence reads as a description of the instrument rather than of a person's discipline. Same
shape as the four already on the board: a statement true over a domain nobody established.

Found 2026-08-27 by the coder, four lines from an edit it was making in `CODER.md` and outside the
task it was working. Verified independently by the architect.

## Why this is not a one-line flip

`TreatWarningsAsErrors=false` was set deliberately by someone. Turning it on globally may fail
builds across generated code, EF migrations and analyzer sets that differ per configuration — the
gate's own header note 9 records the **first Release run exposing `CA1826` warnings that Debug did
not**. A change that turns every existing warning into a build break is a different task from
closing this hole.

**Establish the cost before choosing the mechanism**, the same discipline T-048's Option A is
waiting on and T-056's applock is waiting on. Report how many warnings exist today, per
configuration, before proposing anything.

## Two candidate mechanisms — do not assume the first

1. **`TreatWarningsAsErrors=true`.** Strongest and most invasive: enforces at build time everywhere,
   including a developer's own `dotnet build`, not just under the gate. Cost is whatever is
   currently warning.
2. **Fail the gate on a non-zero `Warning(s)` count.** The grep at :457 already reads the number —
   it is thrown away. Cheaper, no project files touched, and it enforces exactly where the merge bar
   is claimed. **Weaker in two respects, the second raised by the coder and decisive:** it does not
   stop a warning reaching a branch, only one reaching a merge; and **it catches warnings in the
   build the gate performs and nothing about a build it does not.** `--no-build` is on every suite
   invocation, so building once in an IDE and running the gate over that output would report clean
   over a build the gate never saw. **Establish that before choosing this** — it is the same shape as
   the finding itself: an enforcement true over a narrower domain than its wording implies.

There may be a third. The choice is the architect's, but bring the measured warning counts and a
recommendation rather than a menu.

## Done when

- A build that introduces a warning **fails the gate** — demonstrated by planting one, as the red
  path was demonstrated in T-055 rather than argued.
- The existing suite still passes at whatever bar is chosen, with counts against the baseline.
- `CODER.md` and the `DEC-L-008` row on the board are corrected to say what is now **enforced**
  rather than what is expected — and if any part remains convention, it says so in those words.
