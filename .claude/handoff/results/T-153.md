# 1. THE PLACEMENT PROBLEM YOUR RULING EXPOSED, AND WHY THE ENUM IS IN CONTRACTS

`SSAS.HR.Contracts` **references no projects at all** — it is dependency-free by construction, which is why
`EmploymentRecord` uses only primitives. So a purpose-named contract read **could not return an enum defined
in `SSAS.HR.Domain`**, where I first put it.

Three options, and the choice was not free:

```
enum in Domain, mirrored in Contracts    two enums kept in step by hand   -> DEC-L-080
enum in Domain, contract returns string  stringly-typed across a boundary
enum in Contracts, Domain references it  ONE enum                         <- taken
```

**`SSAS.HR.Domain` now references `SSAS.HR.Contracts`.** No cycle is possible — Contracts depends on
nothing — and **the only guard on HR's domain references bars `SSAS.Platform`**
(`The_hr_domain_still_references_no_platform_assembly`), which this does not touch. There is precedent for
enums in a Contracts assembly: `IAttendanceSummary.cs` and `JournalPostingContracts.cs` both hold one.

# 2. ⚠ THE THREE ASSUMPTION GUARDS DID NOT FIRE, AND THE REASON IS THE RULING ITSELF

**You expected them to. They passed unchanged, on the first run, all three.**

The reason is not luck and it is not a weakness in them. **They pin the CALCULATION** —
`PayrollEmployeeInput`, the working-calendar day count, `AttendanceSummaryResult`. **Your ruling put the
employment type on the COMMAND path**: read once, at compensation-recording, to decide whether a record may
exist. **It never reaches a calculation, so nothing they watch moved.**

Had the type gone onto `EmploymentRecord` as a fifth field — the widening `DEC-PAY-0017` refuses — it would
have flowed into the roster, into the run, and **guard 1 would have fired immediately.** The guards firing
was the correct prediction *for the design they were written against*, and the ruling changed the design.

**I have pinned that, so the answer survives the next reader.** Guard 4,
`Employment_type_reaches_the_command_path_and_not_the_calculation`, asserts the enum is real (three members,
by name) and that `SSAS.Payroll.Domain` does not use it. **The file's header, which opened *"employment type
does not exist in this product"*, now says it does and explains why 1–3 still pass.**

## The exposure is unchanged and is now more precise, not less

**A `PartTime` employee is expressible in HR today, and the payroll calculation still cannot tell them from
a full-time one.** T-068's finding stands in full. What T-153 changed is that the assumption is now
*nameable* — and guard 4 fails the day someone acts on it.

## ⚠ The third plant passed, and my comment was wrong about why

I wrote that guard 4 catches *"a reference from the domain"*. **Adding the `ProjectReference` to the
`.csproj` alone leaves it green** — the compiler emits no assembly reference for an assembly no type is
taken from, so `GetReferencedAssemblies()` never sees it. A single *use* reddens it instantly.

**The usage reading is the one worth having** — an unused reference decides no money. But the comment
promised a review of the `.csproj` that the test does not perform, and **a reader relying on that would
have been relying on nothing.** Corrected in place, with the measurement.

## And a count in a comment had been stale twice

`PayrollApiTestHost` said *"`IJournalPoster` and `IEmployeeRoster` are the ONLY routes out of this
module."* **There are four** — FP-013 added `IAttendanceSummary`, T-153 added
`IEmployeeEngagementDirectory` — and the number went stale both times, because `DEC-L-002`: nothing reads
prose.

**The claim itself was always sound, so I did not delete it — I made it executable.**
`The_payroll_host_registers_no_foreign_module_service` asserts no crossing resolves to a foreign module's

it, an unregistered contract would also pass an "is empty" assertion** (`DEC-L-070`).

# 4. `DEC-POS-0023` IS NOT ENGAGED, AND I SAID SO WHERE IT WILL BE FOUND

You asked for the reasoning in the result **and** in the code, because the decision has been invoked
correctly before and a reader finding this without the argument will assume it was missed. It is in the
header of `EmploymentType.cs` and again on `IEmployeeEngagementDirectory`:

> **The test is whether knowing the value tells you what someone is PAID. Employment type does not — it
> tells you HOW they are engaged.** Full-time, part-time and contract are facts about the shape of the
> engagement, and two full-time employees may be paid anything at all. HR has always owned status, dates,
> branch and department on exactly that basis. **The value is a discriminator on the pairing rule, not an
> input to any amount.**

**This also resolves T-107's open tension.** Contract is an employment type whose payment mechanism is
`OneOffPayment` — and `SalaryType` has no member that could express it (`Monthly`, `Daily`, `Hourly` are
all recurring rates). So the refusal is not *"contract employees may only use salary type X"*; **there is
no X**, and a compensation record would make them recur in every run.

# 5. ONE THING I DECIDED WITHOUT YOU, AND YOU MAY WANT IT BACK

**A null employment type is refused separately from a contract one**, with its own error and a 404 rather
than a 409. `GetEmploymentTypeAsync` returns null when HR cannot resolve the employee, and **a handler
testing only `is EmploymentType.Contract` would let that through** — recording compensation against an id
that names nobody. The guard is checked **after** authorisation, deliberately: answering "not found" first
would give any caller who can reach the route a probe for the existence of any employee id.

**Not in your ruling.** It follows from it, but if you would rather a missing employee be some other status
— or be allowed — say so and it is a two-line change.
