# 1. DOES THE RETRY RECOVER ANYTHING A CALLER COULD NOT? **YES, AND T-137 ALREADY PROVED IT.**

**The case is not hypothetical — it is a test that fails on this branch today:**

```
A_first_target_write_records_its_observation_even_when_complete_wins_the_row
  -> TenantStorage.CutoverConcurrencyConflict
```

**A legitimate tenant write is refused because an UNRELATED row update displaced its bookkeeping.**
`CompleteAsync` advances the operation row; the writer's write-once update loses the RowVersion race; the
re-read finds NULL **because `Complete()` never sets the observation**; the store reports a conflict and the
fence — correctly, after T-135 — refuses the write.

**The caller cannot recover from that.** It receives `CutoverConcurrencyConflict` and **has no way to
distinguish "the platform lost a bookkeeping race with itself" from "another writer is genuinely
contending".** Retrying is not something it can decide to do, because from outside those two look identical.

**So the retry converts a refusal that is nobody's fault into a success. That is a real recovery and it is
the answer to your question.**

## And the bound is right

**One retry, not a loop**, with the reasoning stated: *"the only competing non-observation writer is
`Complete()` and it runs once; a loop here would turn a bookkeeping race into an unbounded wait on the
tenant's write path."* **A retry on a write path needs exactly that argument and it has it.**

# ⚠ 2. THE `PermitsWriteTo` RE-CHECK — IT WORKS, AND ITS COMMENT OVERCLAIMS

You asked me to establish whether the re-check genuinely prevents recording an observation for a write the
fence would no longer admit, and said it was the half you could least judge by reading. **It is half right.**

```csharp
// Retrying on "the timestamp is null" alone would record an observation for a write the fence would no
// longer admit — the operation may have moved on, OR A FURTHER CUTOVER MAY HAVE MADE THIS PHYSICAL
// DATABASE THE WRONG ONE.
if (!refreshed.PermitsWriteTo(tenantDatabaseId)) { return Result.Failure(TenantWritesFrozen); }
```

**`refreshed` comes from `ReadWriteGateByOperationAsync`, which filters `operation.Id == cutoverOperationId`
— THIS operation and no other.**

**What it therefore catches:** this operation's own status leaving `RoutingFlipped`/`Completed` — a rollback
or failure between admission and retry. **Real, and worth having.**

**What it cannot catch: a FURTHER CUTOVER.** A second cutover is a **different row with a different Id**, and
a by-Id read cannot see it. **The clause after the "or" is not implemented by this check.**

## What actually guards that case

```csharp
FindActiveWriteGateAsync(tenantId)  ->  .Where(TenantId == tenantId && Status in (Frozen, RoutingFlipped, Completed))
                                        .OrderByDescending(operation => operation.Id)
```

**The fence's own admission lookup takes the NEWEST operation for the tenant.** So a further cutover is
caught **there**, at admission, before the retry is reached — **not by the re-check that claims it.**

**The protection exists. The comment attributes it to the wrong line.** That matters because someone
tightening this later will read that sentence as the reason the by-Id read is sufficient, **and it is
sufficient for a different reason than the one written down.**

# 3. WHAT THE RETRY DOES NOT CHANGE, STATED SO THE SCOPE IS NOT READ AS WIDER

**T-135 already closed the false-negative**, and the branch's own comment describes that world rather than
this one: *"the tenant's write, whose result was previously discarded, committed anyway."* **Since T-135 the
write does not commit, so the platform cannot record that none did while one landed.**

**The retry closes the FALSE REFUSAL, which is a different defect.** They are complementary and the order we
took them in is the safe one — **loud-but-sometimes-wrong before quiet-and-wrong.**
