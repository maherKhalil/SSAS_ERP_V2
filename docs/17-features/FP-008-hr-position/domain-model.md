# FP-008 — Domain Model

> Draft. The **number** of aggregates below is `OD-POS-002` and is not settled. The model is written for the
> three-entity reading; under the other options the grade aggregates collapse or disappear, and every
> statement about them collapses with them.

## The aggregate

`Position` is an aggregate root in `SSAS.HR.Domain.Positions`, implementing `AggregateRoot<Guid>`,
`IAuditableEntity`, `ITenantOwnedEntity`, `ICompanyOwnedEntity`.

**It does not implement `IBranchOwnedEntity`, and that is a decision rather than an omission**
(`DEC-POS-0001`). An architecture guard asserts the absence, for the reason FP-007 recorded: Employee
implements all three dimensions, and a neighbouring aggregate with two reads as an oversight until something
says it is not.

```
Position
  Id                     Guid, never generated by the store (ADR-013)
  TenantId               stamped by the persistence boundary
  CompanyId              stamped by the persistence boundary
  Code                   value object, normalized, unique within company
  Title                  value object, required, not unique
  JobGradeId             Guid?, grade in the same company            (OD-POS-002)
  DepartmentId           ABSENT under the recommended reading        (OD-POS-003)
  ReportsToPositionId    ABSENT under the recommended reading        (OD-POS-006)
  Status                 Active | Inactive
  StatusChangedUtc/By    who moved it and when
  Created/Modified Utc/By  IAuditableEntity, stamped by infrastructure
  RowVersion             concurrency token
```

### What the aggregate does not let you do

There is no setter for `TenantId` or `CompanyId` beyond the ownership interfaces the persistence layer stamps
through. There is no way to set `Status` directly — only `Deactivate()` and `Reactivate()`, each recording
who and when. This mirrors `Department` exactly.

### What the aggregate deliberately does not contain

**No reference to any Employee.** Not an incumbent identifier, not a holder collection, not an association
table pointing from Position to Employee. Who holds a position is answered by querying Employees.

This is `DEC-POS-0002`, and it is the single most important structural constraint in this package. A
`Position → Employee` foreign key of any kind, combined with the `Employee.PositionId → Position` key this
package adds, is a **cycle in the table-level foreign-key graph**. `TenantCutoverCopyPlan.Order` returns
`CutoverCopyOrderUndecidable` when no table is ready, and Shared→Dedicated cutover would stop working for
every tenant. `RISK-DEP-001` verified this in source for the analogous Department manager column, and
`ADR-026` decision 7 is the standing rule.

`ADR-026` decision 7's revisiting condition applies unchanged: if the cutover engine ever gains cycle-aware
two-pass copying, a direct reference becomes available and is the better model.

## Grade aggregates **(OD-POS-002)**

```
JobGrade                                  SalaryGrade
  Id, TenantId, CompanyId                   Id, TenantId, CompanyId
  Code (normalized, unique per company)     Code (normalized, unique per company)
  Name                                      Name
  RankOrder      int, unique in ladder      RankOrder      int, unique in ladder
  SalaryGradeId  Guid?  ───────────────▶    MinimumAmount  decimal(19,4)?   (OD-POS-004)
  Status, audit stamps, RowVersion          MidpointAmount decimal(19,4)?   (OD-POS-004)
                                            MaximumAmount  decimal(19,4)?   (OD-POS-004)
                                            Status, audit stamps, RowVersion
```

**The reference points one way, from Job Grade to Salary Grade, and never back.** A mutual reference would
reintroduce the cycle `DEC-POS-0002` exists to prevent, in a place nobody would think to look for it. The
graph must stay a tree.

### Rank order is data, not a derived reading

`RankOrder` is an explicit integer. It is **not** parsed from the code, and the code is not required to sort
in rank order.

The reasoning is `DEC-POS-0006`. Deriving order from a code string is derived state that can drift — the
trade this codebase refused in `DEC-DEP-0005` and again in `DEC-DEP-0029` — and it is wrong on its own terms:
`"G10"` sorts before `"G9"` under every collation the product uses. Sparse values (10, 20, 30) leave room to
insert a grade without renumbering a live ladder.

**The honest counter-argument is recorded rather than buried:** no current requirement compares two grades.
Nothing promotes, nothing ranks. The field is proposed now because adding order later to a populated ladder
means inventing it retroactively for rows whose intended sequence nobody wrote down — the same not-free
deferral `DEC-DEP-0016` described, and the reason that one was reversed.

## Value objects

`PositionCode`, `PositionTitle`, and the grade equivalents follow the `EmployeeNumber` / `EmployeeFullName` /
`DepartmentCode` pattern already established: construction validates, exposes `Value`, and the code
additionally exposes `NormalizedValue` for the binary-collated uniqueness index.

**No money value object is proposed, and no currency value object is proposed.** See `DEC-POS-0015`: the
product's currency type lives in `SSAS.Platform.Domain`, which `SSAS.HR.Domain` cannot reference, and the
recommended answer is to carry no currency at all rather than to duplicate the type or to reach across the
module boundary. Amounts, if `OD-POS-004` retains them, are plain `decimal?` properties validated by the
aggregate.

## Employee changes

`Employee` gains:

```
  PositionId             Guid, required for employees created after FP-008 (OD-POS-001)
```

and one operation, `ChangePosition(destinationPositionId, reasonCode, reasonText, actor, eventId, occurredUtc)`,
returning the appended `EmployeePositionAssignment` as a `Result<T>`.

`PositionId` gets **no public setter**, exactly as `DepartmentId` has none and `BranchId` has none only
because `IBranchOwnedEntity` requires it for stamping. `ADR-026` decision 6 states this as the pattern rather
than a one-off; `PositionId` is the third ownership-adjacent field and inherits it.

`ChangePosition` refuses, in this order and before mutating anything: a terminated employee, an invalid
actor, an empty destination identifier, and a destination equal to the current position
(`PositionUnchanged`). It never touches `BranchId` or `DepartmentId`.

`StampInitialAssignment` is extended to build and validate the position record **alongside** the existing
department record, before either is attached — the same construct-then-mutate ordering FP-007 Phase 3 used,
so a failure on the second record cannot leave the first written.

## `EmployeePositionAssignment`

```
EmployeePositionAssignment : Entity<Guid>, IAuditableEntity, ITenantOwnedEntity,
                             ICompanyOwnedEntity, IAppendOnlyEntity
  TenantId, CompanyId       stamped
  EmployeeId                the employee this record describes
  SourcePositionId          Guid?  — NULL only on the initial record
  DestinationPositionId     Guid   — never equal to the source
  EffectiveFromUtc          datetimeoffset
  ChangedBy                 nvarchar(256)
  ReasonCode                nvarchar(32)?
  ReasonText                nvarchar(512)?
```

**It mirrors `EmployeeDepartmentAssignment` deliberately rather than inventing a third history shape.** A
reader who knows one knows this one. Specifically, and for the same recorded reasons:

- **Not `IBranchOwnedEntity`.** A position change says nothing about a branch. Stamping one would attach an
  unrelated dimension and put an org-structure change inside the branch write boundary.
- **No `RowVersion`.** A record that is never updated has no concurrency state to protect; concurrent changes
  serialize on `Employee.RowVersion`.
- **No `ModifiedUtc` / `ModifiedBy`.** It is never modified.
- **No `EffectiveToUtc`.** Closing an interval means UPDATING the previous row, which is precisely the
  history mutation the model exists to prevent. The interval is derived by ordering `EffectiveFromUtc`, with
  the identifier as a deterministic tie-break.
- **A null source marks the initial record, and nothing else identifies it.**
- **`internal` factories**, so nothing outside the domain assembly can fabricate a row. The aggregate
  produces the record: `StampInitialAssignment` writes the first in the same unit of work as the Employee, and
  `ChangePosition` appends each subsequent one atomically with the column change.

## Why the column *and* the history

A reasonable reader will ask why `Employee.PositionId` exists at all when the history table already records
the current position as its latest row.

**Because the column is what makes `BR-HR-0006`'s cardinality unrepresentable.** One column holds one value:
two concurrent assignments race on `Employee.RowVersion` and one loses, with no additional mechanism. If the
history table were the sole record, "current" would be a flag or a max-date query, two concurrent assignments
could each insert a current row, and only a unique filtered index (`WHERE IsCurrent = 1`, keyed on
`EmployeeId`) could arbitrate — an index that works, and that arbitrates a race the column shape never
creates.

This is `DEC-DEP-0028`'s lesson restated: there, the primary key on `DepartmentId` was "what makes a second
row unrepresentable, and that is the design rather than a backstop". Here it is the column.

## Domain events

`PositionCreated`, `PositionUpdated`, `PositionDeactivated`, `PositionReactivated`,
`EmployeePositionChanged`, and the grade equivalents that `OD-POS-002` retains.

These follow `ADR-009` and the existing `SSAS.HR.Domain.Events` pattern. They are raised; no handler is
introduced by this package.

## What the domain model cannot settle

Four of its own shapes are owner decisions, and they are marked in the diagrams above rather than resolved:
whether `DepartmentId` appears on Position (`OD-POS-003`), whether `ReportsToPositionId` appears
(`OD-POS-006`), whether the grade aggregates exist and how many (`OD-POS-002`), and whether the amounts exist
(`OD-POS-004`). A domain model that quietly picked one of each would read as settled, which is exactly the
impression this package must not create.
