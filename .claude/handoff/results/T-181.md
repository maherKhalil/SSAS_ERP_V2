# 1. WHAT A COMPANY-SCOPED LOCK WOULD BLOCK THAT IS LEGITIMATE — FIRST, AS INSTRUCTED

**Almost nothing, and the "almost" is a delay rather than a refusal.**

With a key of `SSAS.GL.FiscalYear.Define.{tenantId}.{companyId}` and `@LockOwner = 'Transaction'`:

```
BLOCKED     a second concurrent DefineFiscalYear for the SAME company     <- this is the race
NOT BLOCKED definitions for any other company                            different key
NOT BLOCKED every other GL operation — journals, drafts, accounts,       different prefix; the existing
            period state changes, reports                                locks already coexist this way
NOT BLOCKED anything in any other module
```

**The one legitimate case that waits:** two administrators defining two *different, non-overlapping* years
for one company at the same instant — FY2026 and FY2027. One waits for the other's handler, which is
**two indexed reads and one insert of a year with its periods.** Milliseconds.

**The only way that becomes a refusal is if the wait exceeds the timeout.** At the 5 seconds both existing
domain locks use, that requires a handler doing two indexed reads to take five seconds.

**So the answer to your first question is: the lock costs a legitimate concurrent definition a delay of one
short handler, and costs everything else nothing.**

# 2. WHAT "HUMAN-SCALE" MEANT — AND THE HANDLER SETTLES IT

`DefineFiscalYearCommandHandler` end to end: resolve actor, authorize, `FiscalYear.Create` (validates the
period list), `CodeExistsAsync`, `OverlapsExistingAsync`, `AddAsync`, `SaveChangesAsync`.

**There is no user interaction anywhere in it.** No form, no confirmation, no second request.

So:

- **If "human-scale" meant the USER'S act** — opening a form, typing dates, submitting — **the objection is
  about a design nobody is proposing.** That would be a lock held across a session, and no lock in this
  product does that: every one is scoped to a single handler invocation.
- **If it meant THE HANDLER**, the claim is measurably wrong. The handler is machine-scale, and
  **structurally identical to `ChangeDepartmentParentCommandHandler`, which already holds a lock across
  exactly this shape.**

**Either way the objection does not survive contact with the handler it describes.**

# 3. ⚠ THE PRECEDENT IS EXACT, AND IT POST-DATES THE OBJECTION

`SqlServerDepartmentHierarchyLock` guards the identical problem, and its own header could be pasted into
GL's:

```
                          department hierarchy              fiscal-year overlap
what no constraint holds  a cycle across many rows          a range predicate across many rows
scope                     (tenant, company)                 (tenant, company)
                          "exactly as narrow as
                           correctness allows"
ownership                 Transaction — released by         same available
                          COMMIT or ROLLBACK
timeout                   5 seconds                         same available
frequency argument        "hierarchy moves are rare,        "defining a fiscal year is rare
                           so contention is rare"            and deliberate"
```

**`DepartmentHierarchyCommandHandlers` states the gap in words that fit GL exactly:**

> *"two individually legal moves combining into a cycle that neither transaction could have detected."*

**Substitute "years" for "moves" and "an overlap" for "a cycle" and it is GL's comment.**

## ⚠ And the rarity argument was used to reach BOTH conclusions

**GL:** *"the exposure is small (defining a fiscal year is rare and deliberate)"* → therefore do not lock.
**HR:** *"Hierarchy moves are rare, so contention is rare"* → therefore locking is cheap, so lock.

**The same premise, opposite conclusions, and HR's is the one that closed a race.** Rarity is an argument
about the COST of a lock, not about the acceptability of the gap — GL used it as the latter.

---

# 4. ONE DESIGN CONSEQUENCE, IF IT IS EVER BUILT

**`DefineFiscalYearCommandHandler` opens no transaction** — it calls `SaveChangesAsync` directly. The
department handlers open one and take the lock inside it.

**That is a requirement, not an obstacle, and SQL Server enforces it**: `sp_getapplock` with
`@LockOwner = 'Transaction'` **fails when there is no open transaction**, so a handler that took the lock
outside one would be refused rather than silently getting an ineffective lock. The hierarchy lock's header
records that property as a feature.
