# THE DEFECT, VERIFIED INDEPENDENTLY

```
Hourly   BaseAmount * WorkedQuantity                     observed hours
Monthly  BaseAmount * factor                             prorates on employment dates
Daily    BaseAmount * (StandardWorkingDays - Unpaid)     consulted NEITHER
```

**Measured end to end:** an employee hired on 16 January, a 21-working-day month, 100/day.

```
before T-115   1900   (21 - 2 unpaid, the whole period)
after  T-115    800   (10 - 2 unpaid, the days they were employed)
OVERPAID BY    1100
```

**Both figures observed, not reasoned:** the joiner plant asserted 1900 and failed with `Actual: 800.0000`.

# THE MECHANISM — (B), AND THE EVIDENCE WAS BETTER THAN THE ARGUMENT

**`GetWorkingDaysAsync(companyId, fromDate, toDate)` already existed** on `IAttendanceReadService`, routed at
`GET /calendars/working-days`, justified in terms that describe Payroll exactly: *"clients need the SAME
answer the domain uses — a client computing working days itself would drift from the server the first time a
holiday moved."*

**So `OD-ATT-0009` never barred bounds-shaped working-day counts.** That decision is about the SUMMARY
resolving *which period* covers a date; a working-day count resolves no period. **The capability was public
to HTTP callers and invisible to the one module whose money depends on it**, because it lives in
`Application` and `ADR-012` bars Payroll from referencing that.

**Promoted to `SSAS.Attendance.Contracts`.** Payroll clamps the window it already computes for proration and
asks for the count inside it.

**Returns a plain `int`, not `Result<int>`** — the contracts assembly carries no `Result<T>` and reports
outcomes as values a caller must handle. **Zero means "could not answer", which is the same fail-closed zero
`NotAvailable` gives.**

## And `StandardWorkingDays` was removed rather than left unconsumed

T-108 added it, two tasks ago, for exactly this job. **It was the wrong quantity: a period total cannot
express a window inside itself.** Leaving it would have been `PayElement.OvertimeTier`'s shape.

**Guard 3 fired and was answered for a REMOVAL** — the first time. The answer matters: **the employee
dimension never entered the contract, which is what that guard exists to prevent, and the fix is why the
field left rather than a reason to make it employee-aware.** Clamping inside `GetForPeriodAsync` was refused
for exactly that reason.

# ⚠ THE BEHAVIOUR THAT HAD TO CROSS, AND IT IS THE PART THAT NEEDED PROVING

The architect caught this before I built it: **the two facts now come from two calls, and they fail
differently.** `GetWorkingDaysAsync` reads the COMPANY's calendar — it knows nothing about whether this
employee's attendance arrived, **and would happily answer 21 while `UnpaidAbsenceQuantity` stayed zero.**

**A daily employee would have gone from REFUSED to PAID IN FULL, silently.**

**Kept by leaving the count on the `Available` branch**, so an unavailable summary still yields zero and the
calculator still refuses. **The reasoning moved with it** — that paragraph lived on the field T-115 deleted,
and `DEC-L-080` says one place states it.

**Proved at SOURCE, not by assertion.** I removed the `Available` branch and re-ran:

```
guard removed  ->  the run CALCULATES SUCCESSFULLY where it must refuse
guard restored ->  Payroll.DailySalaryHasNoWorkingDays
```

**That is the only way to know the behaviour crossed rather than looked like it crossed.**

**Unmapped since T-107 declared the constant.** A daily employee with no working days would have received a

correctly.

**Mapped to `RunStateInvalid` (409)**: the request is well-formed and the world is not ready, which is
`AttendancePeriodOpen`'s shape rather than `NothingToCalculate`'s. **There IS something to compute; the
input it needs is absent.**

**I have not established why it went red now rather than in T-107, and I am not going to invent a reason.**
The mapper never named the code, so either the register's closure reached it for the first time in T-115 or
it was under-reporting before. **Worth someone's time; the fix is correct either way.**
