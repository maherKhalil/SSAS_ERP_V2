# T-047 — The `Restrict` loop and ownership foreign keys

- **Branch:** `agent/T-047-ownership-delete-behaviour` — branch from `main`
- **Module:** BuildingBlocks + Platform
- **Issued:** 2026-08-26
- **Depends on:** T-043 merge (PR #90). **Gated.**

## Goal

You found the real cause. `PersistenceDbContext.OnModelCreating:43` sets **every** foreign key to
`Restrict`, ownership FKs of owned collections included — and the snapshot format cannot serialise a
delete behaviour for owned relationships, so ownership implies `Cascade` on rehydration. Model says
`Restrict`, snapshot says `Cascade`, **and the differ is right.**

**Every migration scaffolded in this repository carries six spurious operations until this is settled.**

## My view, which is the thing to disagree with

**Exclude ownership FKs from the loop.** Three reasons, and I want the third tested rather than taken:

1. **`Restrict` on an ownership FK is semantically meaningless.** An owned entity's lifetime is
   definitionally bound to its owner; owned rows have no independent existence and cannot be deleted
   separately. "Refuse to delete the owner while owned rows exist" is a rule that can never be
   satisfied except by deleting rows EF manages for you.
2. **It is unexpressible**, so the disagreement is permanent. And **committing the operations once does
   not fix it** — you established it is self-regenerating, so that path means deleting six operations
   by hand from every future migration forever.
3. **The loop's intent survives.** Whatever it was written for — and it carries **no comment at all**,
   which I will come back to — that intent is about *reference* FKs between aggregates. Excluding
   ownership FKs preserves it exactly.

**The cost, stated plainly: this is a real schema change.** The database has `Restrict` on those three
FKs today, so excluding them from the loop produces a genuine migration altering them to `Cascade`.
That is correct rather than incidental — but it is a change to delete behaviour on a base context four
modules depend on, and it must be deliberate.

**Disagree in writing if you disagree.** I am not confident about one thing in particular: whether
there is any case in this codebase where an owned collection *should* restrict. I could not construct
one. If you can, that changes the answer.

## Acceptance criteria

- [ ] **The loop no longer sets a delete behaviour on ownership foreign keys** — or, if you argue the
      other way, the alternative is implemented with its reasoning in the file. Either way the outcome
      is: **a freshly scaffolded no-op migration is empty.** Demonstrate that, do not assert it.
- [ ] **The loop gains the comment it has never had.** It is the only construct in that file without a
      stated reason, and it has now cost two wrong diagnoses and a task. Say what it is for, and say
      what it deliberately no longer touches.
- [ ] **The accompanying migration is generated and reviewed as a real schema change** — three FKs from
      `Restrict` to `Cascade`, named as intentional, with `DEC-L-039` applied to its comment.
- [ ] **A guard asserts the property, not the instance.** Something that fails if a future ownership FK
      acquires an explicit delete behaviour again — otherwise this recurs the next time someone extends
      the loop. `DEC-L-016`: demonstrate it firing.
- [ ] Gate green under `DEC-L-008`, **Integration runs against real SQL** — this changes delete
      behaviour on a context four modules depend on, and Integration is the only leg that can prove the
      database accepts it. Merged on green. Baseline: Architecture 506, Platform 1032, API 724,
      HR 326, Finance 46, Payroll 56, Attendance 59, **Integration 803 both configurations**.

## Design constraints

- **Do not weaken the loop to make a diff go away.** The test is whether the change is *correct*, and
  the empty scaffold is the consequence rather than the goal. If excluding ownership FKs turns out to
  be wrong, the right answer is to live with the six operations and document why.
- **A schema change to delete behaviour is not a refactor.** Say in the migration what it changes and
  why it is safe — these aggregates are archived rather than deleted, so the behaviour has likely never
  fired, but **"has never fired" is not "cannot fire"** and the migration should not claim it is.
- **`DEC-L-043`:** if the scaffold is not empty after the change, find out which is wrong before
  recording either.
