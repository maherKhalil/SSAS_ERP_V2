# 1. WHY NO FILTER — THE STATES THIS DOMAIN ALREADY TREATS AS LEGITIMATE

**You asked me to enumerate them before choosing, the way T-150 was ruled. I did, and the enumeration is
unusually short: `LeaveBalance` HAS NO LIFECYCLE.**

```
fields        EmployeeId, LeaveTypeId, PeriodYear, EntitlementQuantity, ConsumedQuantity
              + tenant/company/audit/RowVersion
status        NONE. No state enum, no IsActive, no soft-delete, no superseded/replaced marker.
mutations     SetEntitlement, Consume, Release — ALL on an existing row
creation      EXACTLY ONE site: LeaveCommandHandlers.cs:184, inside the upsert
reads         GetForEmployeeAsync(company, employee, leaveType, year) -> LeaveBalance?  (SINGULAR)
```

**Every row is live. There is no state in which a second row on that key is legitimate**, because there is
no state at all — nothing to be superseded, cancelled or rejected.

## ⚠ THIS IS WHY IT DIFFERS FROM T-148, AND THE DIFFERENCE IS THE WHOLE ANSWER

`AttendanceLeaveRequests` needed `HasFilter("[Status] IN ('Submitted', 'Approved')")` **because a rejected
or cancelled request legitimately coexists with an active one** — an unfiltered constraint there would have
refused a legitimate resubmission, which is exactly the failure T-150 was ruled to avoid.

**`LeaveBalance` has no `Status` column to filter on and nothing that would want one.** A filter here would
be machinery guarding against a state the aggregate cannot enter.

**So the answer is "none" for a reason, not by default** — and if someone later adds a lifecycle to this
aggregate, the index is the thing that must be revisited.

# 2. WHY 409 AND WHY IT IS RETRYABLE

The race: two callers both read `GetForEmployeeAsync` as null, both take the `LeaveBalance.Create` branch,
both insert. **The handler opens no transaction** — it is a plain read then `SaveChangesAsync`.

**With the index, the loser fails at commit and should be told `Attendance.LeaveBalanceConflict`, which is
already declared and already mapped to `Conflict` (409) at `AttendanceApiErrorMapper.cs:107`.** The code
that T-167 found unreferenced is the code this needs — it was written for this and never wired.

## ⚠ RETRYABLE, AND THAT IS THE DISTINCTION YOU DREW ON THE REVERSAL RACE

**A retry succeeds.** The second attempt finds the row the winner created and takes the `SetEntitlement`
branch — which is the operation the caller wanted. **Setting an entitlement twice concurrently converges.**

That is the opposite of the already-reversed race, where retry can never succeed. **Same status code,
opposite correct client action** — so the answer must say which, and 409 with a retryable code does.

## The translation is safe here for T-165's reason, checked rather than assumed

`SetLeaveEntitlementCommandHandler` writes **only** `LeaveBalance`, and after this change `LeaveBalance`
carries **exactly one** unique index. **One reachable index means the handler can name it**, which is the
condition that made the posting translation sound and the reversal translation unsound.
