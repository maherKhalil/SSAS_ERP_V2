## What changed, and what deliberately did not

`GATE_SCOPE` defaults to `TASK`. `GATE_MODE` is untouched and orthogonal: **mode is what the box can
afford, scope is what question is being asked.** Folding them together would make the cheap answer
unavailable on a build box and the thorough one unavailable here.

**Scope changes exactly two variables** — the configuration list and the suite list. Preconditions, both
memory floors, the sibling-`testhost` refusal, `SSAS_%` reaping, build, blame collection, sampling,
status capture, the greps and the terminal `exit $GATE_FAILED` are shared and untouched. That is what
makes `PHASE` the gate that existed rather than a reimplementation of it.

### One deviation from the specification, ruled correct

T-055 specified `TASK` as *"Architecture, Platform, HR, API, plus the changed module's suite."*
**Implemented as all seven non-Integration suites, with no diff inference.**

The three module suites cost **23, 24 and 25 milliseconds**. Selecting between them buys back under a
tenth of a second in exchange for an inference over the diff — **the same trade the task refuses for
Integration, at a hundredth of the saving.** A strict superset can never run less; a selection can
silently omit a suite, and a suite nobody runs looks exactly like a suite that passed.

The architect ruled the deviation correct and **the specification inconsistent with itself**: it refused
the inference where it saves 32 minutes and required it where it saves 72 ms, in adjacent paragraphs.

### Integration is opt-in and never inferred

`GATE_INTEGRATION=1` under `TASK`; always on under `PHASE`, where setting the variable prints that it is
ignored rather than silently obeying or discarding it. The coder knows whether `DEC-L-008` condition 3
applies; a script reading the diff would be guessing, **and a guess wrong in the permissive direction is
a silent hole in the merge bar.**

### An unrecognised value aborts rather than defaulting

Exit **6**, distinct from 1 and from the 2–5 precondition codes. `GATE_SCOPE=PAHSE` would otherwise have
run the cheap gate and reported it under the thorough one's name — **and the log would look right.**

```
GATE_SCOPE=PAHSE                     -> exit 6
GATE_INTEGRATION=yes                 -> exit 6
GATE_SCOPE=PHASE GATE_INTEGRATION=0  -> runs Integration, says the variable is ignored
```

### The verdict names its scope

`[GATE GREEN -- TASK scope: seven suites, NO Integration, Debug only]`. `[GATE GREEN]` alone was
unambiguous while there was one gate; with two, **the cheap scope is the one that will be read as the
thorough one, because it is the one that gets run.**

## The red path — verified by run, not by reading

The architect flagged this as the thing they most expected to be got wrong, and decomposed it better than
the three options I offered.

**(a) Does a red suite survive later green ones?** The T-016 defect shape is `GATE_FAILED=$?` per suite
instead of a latch. **Tested in a throwaway worktree with the failure planted in the FIRST suite**, so it
had to survive six subsequent passes:

```
!!! Architecture.Tests (Debug) EXITED 1
Failed! - Failed: 1, Passed: 509, Total: 510      <- first suite
Passed! 1032 · 326 · 724 · 46 · 56 · 59           <- six greens after it
[GATE RED -- TASK scope: seven suites, NO Integration, Debug only]
gate exit: 1
```

**A red *last* suite would have proved almost nothing.** The main tree never held the fixture and the
worktree was removed.

**(b) Does the flag survive the configuration loop?** Structural, and definitive in a way reading intent
is not:

```
251:  GATE_FAILED=0     <- once, 181 lines above the configuration loop
432:  for CFG in $GATE_CONFIGS; do
496:      GATE_FAILED=1  <- a latch, not =$?
533:  exit $GATE_FAILED
```

**Three assignments, one writes zero.** A per-configuration reset is not merely absent — it is
unrepresentable without adding a line.

## `PARTIAL` — the memory sampler did not run, in either leg

**`DEC-L-022`'s memory observation is missing for this run, and it is reported here rather than
omitted.**

```
=== Integration.Tests (Debug) ===
The argument '/c/Users/.../scripts/sample-mem.ps1' to the -File parameter does not exist.
awk: fatal: cannot open .../mem-Integration-Debug.csv: No such file or directory
Passed! - 806/806 ... 32 m 48 s
```

**Two failures printed into the log; neither touched `GATE_FAILED`; the leg reported green.**

**The cause was in the launching shell, not in the script**, and was tested rather than inferred:
`export MSYS_NO_PATHCONV=1` suppresses exactly the Git Bash path conversion that `powershell.exe -File`
depends on. Same command, same file: unset runs clean, set produces the error above verbatim. That
habit came from a board entry that named a real remedy without naming where it must not be applied —
now `DEC-L-056`.

**Not re-run.** The architect ruled it, and the reasoning is worth keeping: `DEC-L-008`'s conditions are
about suites, every suite ran, and sixty-nine minutes to recover a curve for a scoping change to a shell
script is not a trade worth making.

### And the finding underneath it, which is not about this run

**When the sampler works the log gains a `--- memory:` line; when it dies the log gains nothing.**
Absence reads identically to not-applicable, and nobody reading `[GATE GREEN]` would notice the
instrument was dead. The header's argument that sampling *"can never fail a gate"* is correct and
untouched — but it argues about a sampler that **runs and reports**. A one-line *"sampler did not run"*
costs nothing, fails nothing, and makes the difference legible. **Queued into T-056.**
