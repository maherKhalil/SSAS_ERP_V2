# T-015 — The seven older `PlatformDbContext` guards are reachable past

- **Branch:** `agent/T-015-platform-guard-fence` — branch from `main`
- **Module:** Platform
- **Issued:** 2026-08-25
- **Depends on:** T-014 (merged, PR #57)

## Goal

You found this while building T-014's guard and correctly refused to fold it in. It is now the
highest-value open item on the board.

`PlatformDbContext` carries seven guards hung on `SaveChangesAsync(CancellationToken)` alone —
tenant deletion, support-principal deletion, permission-assignment deletion, authentication history,
localization history, identity ownership, storage registry. EF Core routes the convenience overloads
inward by virtual dispatch, so **`SaveChangesAsync(bool, ct)` or any synchronous `SaveChanges` commits
straight past all seven.** `PersistenceDbContext` documents this dispatch behaviour itself.

Latent, not live — current callers use the guarded path. But "no current caller does the wrong thing"
is a coincidence that holds until someone writes the obvious line, and these are deletion guards on
tenancy and authorization.

Your own comment at `PlatformDbContext.cs:141` records the defect in the production file. This closes it.

## Acceptance criteria

- [ ] All seven guards are enforced on the **innermost overloads**, so no `SaveChanges`/`SaveChangesAsync`
      path on this context reaches past any of them. Match the fence T-014 established.
- [ ] **A test per guard that fails without the fence and passes with it**, exercising the bypass route
      specifically — not the already-guarded outer path. Seven guards, and the bypass is the point:
      a test that only calls `SaveChangesAsync(ct)` would pass before and after and prove nothing.
      Prove it the way you proved T-014: remove the fence, watch them fail, restore, report both.
- [ ] The comment at `:141` is updated or removed — it currently says these seven are reachable past.
      When they are not, that comment becomes false, and a stale warning is worse than none.
- [ ] The existing architecture guard is **strengthened from "the context fences both overloads" to
      "every guard on the context sits at the fence"**, if that is expressible. If it is not, say why
      in the result rather than leaving the weaker assertion unremarked — I recorded on the board that
      the current guard passes while these seven are bypassable, and that stops being true here.
- [ ] Gate green under `DEC-L-008`, **including `Integration.Tests`** — this touches persistence on a
      context four modules depend on. Counts against the board baseline: Architecture 465, Platform 969,
      HR 326, API 685, Payroll 56, Attendance 59, Finance 46, **Integration 782 both configurations**.

## Design constraints

- **This is a behavioural change to shipped guards.** Code that previously committed via the
  convenience overload will now throw. That is the point, but it means the risk is real — if any
  existing caller or test uses those overloads, it changes behaviour, and the suites are how you find
  out. A failure in an unrelated module here is signal, not noise: report it, do not route around it.
- **Match T-014's fence exactly.** One behaviour, not two dialects of one.
- Zero warnings.
