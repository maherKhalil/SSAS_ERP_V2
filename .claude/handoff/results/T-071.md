# T-071 result — what a self permission would cost. Measurement only.

- **Status:** PENDING MERGE. **Non-gated** — one result file, **nothing built.** Not one line under `src/`.
- **Branch:** `agent/T-071-self-permission-cost`, from `ClaudeBranch` at `53620aa`
- Every claim below is file and line in the tree at that commit.

## The headline: the ruled spelling cannot exist, and its refusal is already under test

`OD-SS-0001` expresses the ruling as `payroll.payslip.view.self`. **That string is four segments, and
a permission name is exactly three.**

```
PermissionName.cs:36        segments.Length == 3 && segments.All(IsIdentifierSegment)
```

Not a convention — a hard equality inside `PermissionName.Create`. A four-segment name fails
`Create`, and `ComposedPermissionCatalog.cs:106-112` throws on that failure and **refuses the whole
composition**, so the application would not start.

**This is not an inference. It is asserted:**

```
ComposedPermissionCatalogTests.cs:143   [InlineData("Far.Too.Many.Segments")]
```

A four-segment contributed name is already a test case for *refuses the composition*.

**Case is a separate matter and a weaker one.** `payroll.payslip.view` — three segments, lowercase —
**would pass the grammar**: `IsIdentifierSegment` (`PermissionName.cs:41`) accepts any ASCII letter,
upper or lower. It would fail `PayrollArchitectureTests.cs:168`, which asserts `segments[0] ==
"Payroll"` ordinally. So the plane's capitalisation is enforced by the module's own guard, not by the
grammar, and the two failures have different causes and different fixes.

### The codebase already names an expression of the same ruling

The task said not to assume `.self` is the shape, and the tree points somewhere specific:

```
PayrollPermissionNames.cs:68-72
  "Self-service is NOT here, and its absence is deliberate. OD-PAY-0016 deferred it ...
   Adding a `Payroll.Payslips.ViewOwn` on an unverified assumption is exactly the shape of the
   FP-011 near-miss."
```

**`Payroll.Payslips.ViewOwn` is three segments, correctly-planed, and fits every guard in the tree.**
It carries "own" in the ACTION segment rather than as a fourth. `REQ-ATT-0023` / `AC-ATT-0032` assert
that this exact permission does not exist — so the requirement and the code are already speaking one
vocabulary, and it is not the ruling's vocabulary.

**I am not proposing a naming convention, which the task forbids.** I am reporting that the existing
one has a three-segment ceiling, that `.self` breaches it, and that a prior file in the same module
already wrote down a spelling that does not.

## 1. How a permission is defined today, and in how many places

**Two files for a business module, and nothing else.**

| # | File | What goes in |
|---|---|---|
| 1 | `PayrollPermissionNames.cs:26-73` | a `public const string` — the one source of the string |
| 2 | `PayrollPermissionCatalogContributor.cs:17-48` | a `ModulePermissionDefinition(name, description)` |

**The Host needs no change.** `Program.cs:100` registers `PayrollPermissionCatalogContributor` once
(HR `:91`, GL `:96`, Attendance `:105`); a new permission inside an already-registered contributor is
invisible to composition wiring.

**Platform's own permissions are a different, three-place shape:** `PlatformPermissionNames.cs`, then
`PlatformPermissionCatalog.cs:11-38` (`Define(...)`, with an optional third argument for scope), then
`PermissionCatalogTests.cs:97-99`, which asserts the exact totals `26 / 22 / 4` and therefore **must
be edited by hand for every Platform addition.** That is deliberate: the comment at
`PermissionCatalogTests.cs:95-98` says the count is asserted *"so a new permission cannot enter the
catalog without someone deciding which plane it belongs to."*

**To be reachable rather than merely defined, a third and fourth place:** an endpoint requiring it via
`PermissionAuthorizationDefaults.CreatePolicyName` (`:10-18`), and the route inventory at
`PayrollRouteInventoryTests.cs:14-40`, which is asserted exhaustively (below).

## 2. What asserts the catalog is complete, and what it would demand

### The guards that fire on a half-built addition — the useful finding

**A constant without a contributor entry, or the reverse:**

```
PayrollArchitectureTests.cs:150                       Every_named_permission_is_defined_by_the_catalog_contributor
GlArchitectureTests.cs:152                            the same guard, GL
AttendanceArchitectureTests.cs:287                    the same equality, inside the anti-self guard
ModulePermissionContributionArchitectureTests.cs:198  the same guard, HR
```

**All four modules have it**, reflected in four different files. It is the FP-006P guard — HR's
constants existed, no catalog defined them, and every Employee endpoint refused every caller — and it
is precisely the thing that catches a permission that was named but never registered.

**Shape:**

```
PayrollArchitectureTests.cs:168     Assert.Equal(3, segments.Length); Assert.Equal("Payroll", segments[0])
AttendanceArchitectureTests.cs:312  Every_attendance_permission_follows_the_three_part_grammar
GlArchitectureTests.cs:175          Every_permission_name_has_exactly_three_segments_and_the_gl_plane
PermissionCatalogTests.cs:72, :84   Assert.Equal(3, identifier.Split('.').Length)
```

**Five independent assertions of three segments, across four files**, plus the composition throw and
the test case above. A `.self` addition fails all of them.

**Description:** `PayrollArchitectureTests.cs:178-188` requires a non-blank description longer than
20 characters — a placeholder is red. `ComposedPermissionCatalog.cs:114-119` refuses a blank one at
startup.

**Route surface:** `PayrollRouteInventoryTests.cs:42-56` asserts the payroll route set **is exactly
the documented inventory**; `:60-70` that every route requires a permission; `:74-84` that each route
requires the permission the inventory names. A self-service endpoint added without updating the
inventory is red; one added to the inventory but requiring the wrong permission is red.

**What none of them assert: there is no exact-count guard on the composed catalog.**
`ComposedPermissionCatalogTests.cs` tests composition *behaviour* — ordering, duplicates, shadowing,
malformed names, laziness — but no total. `PermissionCatalogTests.cs:97` counts
`PlatformPermissionCatalog` only, so a module-contributed permission passes it untouched. **A
correctly-shaped module permission therefore enters the catalog without any guard counting it.** Not
a defect on its own — the per-module equality guards make an accidental addition hard — but the
"someone decided which plane this belongs to" ceremony that Platform additions get, module additions
do not.

### The guard that would have to be amended, and it exists only in Attendance

```
AttendanceArchitectureTests.cs:287
  No_self_service_permission_is_declared_because_the_subject_cannot_be_resolved
    Assert.DoesNotContain(constants, name => contains "Own" || "Self" || "Mine")   // case-insensitive
```

**An Attendance self permission fails this by construction, whatever it is called** — `ViewOwn`,
`.self`, or `Mine`.

**The asymmetry is the finding.** Payroll has no equivalent. `Payroll.Payslips.ViewOwn` trips **no
forbidding guard at all** — it satisfies the three shape guards automatically and enters the catalog.
So the ruling's two modules (`OD-SS-0002`: attendance and payroll) cost different things: Payroll is
two lines and nothing objects; Attendance is two lines plus a deliberate assertion someone has to
take down.

**And that guard states its own reason:** *"Self-service is deferred because it depends on a mapping
from the authenticated identity to an employee record, and this build does not assert such a mapping
exists — verified, not assumed."* **That reason still appears to hold in code** (see *Unestablished*).
Amending the guard is a legitimate specification change once the mapping lands; **it is not something
to delete to make a build green**, and the difference between the two is whether the mapping exists at
the time. Flagged because the guard is worded so that removing it quietly would read as a weakening.

## 3. Whether `.self` belongs to an existing scope concept — no, and it cannot

**Answer: an ordinary tenant-assignable permission. There is no scope it could belong to, and that is
unrepresentable rather than merely unconventional.**

```
PermissionScope.cs:3-7               enum { Tenant = 1, PlatformSupport = 2 }      two values, no third
ModulePermissionDefinition.cs:22     record (string Name, string Description)      NO scope property
ComposedPermissionCatalog.cs:131-135 stamps PermissionScope.Tenant
```

`ModulePermissionDefinition.cs:5-14` says why the type has no scope: *"A `Scope` property here would
be a field a future module could set to `PlatformSupport` and a reviewer would have to notice; with no
property there is nothing to review, and the escalation cannot be expressed."* **A business module
cannot ask for any scope.** The composer stamps `Tenant` unconditionally.

**`PlatformSupport` is the opposite of what a self permission needs.** It is cross-tenant operator
authority that is never tenant-assignable — `Role.AssignPermission` refuses it outright at
`Role.cs:150-153`, and `TenantPermissionClaimFilter.cs:27-28` drops it from tenant tokens as defence
in depth. A self permission must be tenant-assignable to reach employees, so `PlatformSupport` is
excluded by its own definition, not by preference.

**The distinction the task asked to settle, settled from code:** a self permission would be **an
ordinary tenant-assignable permission whose action segment says "own"**. There is no second axis. The
only way `.self` could be a *scope* is a third `PermissionScope` value plus a `Scope` property on
`ModulePermissionDefinition` — the exact field that type was written without, for a stated reason.

## 4. Who grants it

**The path, and every gate on it:**

```
AssignPermissionToRoleCommandHandler.cs:28-31   catalog must define the name  -> InvalidPermission
Role.cs:140-142                                 RoleType.System               -> ProtectedSystemRole
Role.cs:145-148                                 Status != Active              -> RoleNotAssignable
Role.cs:150-153                                 Scope != Tenant               -> PlatformPermissionRejected
Role.cs:155-158                                 already assigned              -> DuplicatePermissionAssignment
```

A user then holds it by role: `AccessTokenClaimsProvider.cs:57-80` reads the user's non-retired role
assignments, unions the permission rows of those roles, and `:83-95` emits them as claims after the
tenant-scope filter.

**So a tenant grants it by: an Active `Custom` role, assign the permission to it, assign that role to
a user.**

### Whether a mechanism exists to grant it to every employee — it does not

**There is no seeding of any kind.**

```
Role.CreateSystem   defined at Role.cs:73   —   called nowhere in src/ (one grep hit: the definition)
```

No system role is ever created by the product. And a system role could not carry it regardless:
`Role.cs:140-142` refuses **every** permission assignment to `RoleType.System`. There is no default
role, no bulk assignment, and no all-users grant on the Platform application surface.

**Granting self-service to every employee today is therefore N individual role assignments**, one per
user, after an administrator creates the role. **That mechanism is the gap, not the permission.**
`AC-SS-0006`'s own phrasing — *"granting every employee self-service"* — describes an act the product
has no way to perform in one step.

I am reporting the absence. **Designing the mechanism is not this task's**, and I have not.

## The question behind all four: does anything make the implication by accident?

# No. Nothing in the current model would grant the administrative permission along with a self one.

**Stated explicitly, as the task asked, because `authorization-model.md` will rest on it.** Six places
it could have lived, each checked:

**1. Evaluation is ordinal string equality on the claim, on both planes.**

```
PermissionAuthorizationHandler.cs:19-21          StringComparer.Ordinal.Equals(claim.Value, requirement.Permission)
PlatformPermissionAuthorizationHandler.cs:29-31  the same, plus a scope check
```

No prefix comparison, no wildcard, no `StartsWith` between two permission names anywhere.

**2. There is no hierarchy type to hold an implication.** `PermissionDefinition.cs:6` is
`(PermissionName Name, PermissionScope Scope, string Description)` — no parent, no `Implies`, no
children, no group. A permission has nowhere to record that it entails another.

**3. Grants are stored and read per exact name.** `RolePermissionAssignment` rows carry one
`PermissionName` each (`Role.cs:160`), and `AccessTokenClaimsProvider.cs:73-80` selects those names
straight into claims. **There is no expansion step between the grant and the claim** — nothing walks,
widens, or derives.

**4. No seed bundles anything, because there is no seed.** `CreateSystem` is uncalled; no default role
exists; nothing ships a pre-populated permission set.

**5. Catalog lookup is exact, and this is asserted.** `PermissionCatalogTests.cs:54-60` proves a
case-variant and a leading space both fail `TryGet`; `ComposedPermissionCatalogTests.cs:185`
(`Contributed_lookup_is_exact_and_ordinal`) proves the same for contributed names.

**6. The one thing that looks like a prefix rule and is not.** These exist and a reader will find
them:

```
PermissionAuthorizationDefaults.cs:24            policyName.StartsWith(PolicyPrefix)
PermissionAuthorizationPolicyProvider.cs:14-24   three more
```

**They operate on ASP.NET policy names, not permission names.** `CreatePolicyName` prepends the policy
prefix (`:10-18`) and `TryGetPermissionName` strips it back off (`:20-37`) to recover the permission.
The prefix is the policy namespace; **no permission is ever compared to another permission.** Named
because it is the only prefix logic in the authorization stack, and misreading it would produce the
opposite answer to the one above.

**`AC-SS-0005`, the reverse direction, holds by exactly the same six lines** — the model is symmetric
because it does nothing whatever beyond an exact match.

### The adjacent risk, which is not an implication but sits next to one

**Two grammars disagree about segment count.**

```
PermissionName.cs:36               exactly 3 segments             catalog side
AuthorizationNameValidator.cs:5-44 ANY number of segments >= 1    endpoint side
```

`PermissionRequirement.cs:7-9` validates with the second. So
`PermissionRequirement("payroll.payslip.view.self")` **constructs successfully**, and an endpoint can
require a permission name the catalog can never define.

The two failure modes differ, and each is quiet in its own way:

- **Name contributed as well** — `ComposedPermissionCatalog` throws at startup. Loud, immediate, safe.
- **Name required at an endpoint but never contributed** — the endpoint answers 403 to every caller
  forever. **That is FP-006P's incident verbatim**, and no test would catch it, because tests mint
  permission claims directly and never travel the assignment path — which is the sentence FP-006P is
  written around (`IPermissionCatalogContributor.cs:9-14`).

**This creates no accidental implication. It creates a silent refusal.** Named because the ruled
spelling is precisely the string that would trigger it, and because the divergence is invisible from
either file alone.

- **I did not audit every module guard exhaustively.** The four `named == contributed` guards and the

- **I did not establish what a self-service ENDPOINT costs** — routing, handler, read scope, the
  `AC-SS-0007` no-identifier contract. The task asked about the permission and I stayed there.

## For the architect
